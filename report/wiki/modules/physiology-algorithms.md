# 生理指标与睡眠分期

已经查清的是：设备会先处理和整理传感读数，手机再从云端接口取得心率、呼吸和睡眠等结果。真正怎样从波形中分出心跳与呼吸、去掉翻身干扰、结合多个传感器，并判断清醒、浅睡和深睡，完整代码还没有取得。云端参与了结果交付，但现有证据仍不能证明“全部计算都只在云端”。

本页按算法链解释哪些运算已经可写成公式、哪些只能看到结果。需要逐函数细节时，继续读 [本地前处理的公式与伪代码](../algorithms/local-preprocessing.md)，或 [指标与睡眠分期的客户端处理](../algorithms/results-and-staging.md)。两份详解分别覆盖真实样本的 MCU/主控代码和 APK 中读取和使用结果的代码。

## 算法链与覆盖范围

设备先记录和整理读数，之后才涉及“人在不在床上、睡到了哪个阶段”的判断。下面把已经追到具体代码的步骤，与目前只能看到结果的步骤分开。

| 阶段 | 已恢复内容 | 仍缺内容 |
| --- | --- | --- |
| 传感前端 | ADC硬件滤波、signed24转换、PGA与软件增益、通道映射、IMU初级配置 | 物理传感布局、现场标定、运行参数绑定 |
| 采样整理 | 缓存新鲜度、打包、时间锚点、秒桶、补点与缺值、上传数组 | 当前实机的实际丢失/重放率和端到端影响 |
| 出站保留 | Frank 发送队列满拒新、发布失败保留队首；NATS 目标配置超额淘汰旧消息 | 实际发布时序、服务端接收记录与遗漏/重复率 |
| 生理提取 | App 结果字段和已追原始数据出口 | 心呼吸频带、检测器、异常搏处理、质量判据与融合 |
| 在床与分期 | 五类阶段字段约定、presence/sleep 版本元数据 | 模型、权重、推理窗、阈值、平滑与个体适配 |
| 健康和分数 | 服务端值、基线、异常标志、SFS/SQS/SRS 消费者 | 生成规则、统计窗口、训练与校准公式 |

本地 ADC 的 sinc 滤波与 IMU 配置属于采集前端；把它们叫作完整的心脏/呼吸信号分离并无依据。缓存可能保留旧值、上传前也会补点和重排；因此“原始上传”不能理解为每点都未经处理、全新且严格同步。[前端 DSP](../../evidence/analysis/sensor-mcu/FRONTEND_DSP_ZH.txt) · [采样新鲜度](../../evidence/analysis/sensor-mcu/SAMPLE_FRESHNESS_ZH.txt)

## ADC 滤波公式与适用条件

这一步会平滑数字读数，并减少输出的数据量。它只是采集时的一道处理，还没有把混在一起的心跳和呼吸分别取出来。

已恢复的正常稳定转换配置为 sinc3 抽取 1024，再接 sinc1 抽取 8。令 z 的一个延时对应一个调制器周期：

```text
H(z) = [(1 - z^-1024) / (1024 × (1 - z^-1))]^3
       × [(1 - z^-8192) / (8 × (1 - z^-1024))]

f_out = f_mod / 8192
半功率频率 / f_out = 0.437072842
稳态群延迟 = 0.624816895 个输出周期
```

它平滑并抽取 ADC 转换序列。已追写链没有开启额外 DCBLOCK，也没有给出分别提取呼吸与心搏的两套实际使用的滤波器。DC 增益为 1，因此不能把这个滤波块解释为已经去掉直流、自动分出呼吸和心跳。

只有假设真实输出率为 500 SPS时，半功率点才换算为约 218.536 Hz，稳态数字滤波群延迟约 1.249634 ms。当前实机的最终时钟分频与 ADC 物理连线仍未验证；这些绝对单位不是实测，也不包含机械耦合、模拟前端或传输延迟。启动后首个稳定样本的时间与稳态群延迟是不同量。[滤波推导与卷积互证](../../evidence/analysis/sensor-mcu/ADC_FILTER_DERIVATION.txt)

## 数值转换与缓存复用

程序会把芯片读出的字节变成带正负号的数，再放进暂存区。新数据没准备好或读取失败时，暂存区可能继续保留上一次的读数。

Sensor MCU 的 `0x0801D7DC` 逐通道写值链可概括为下面的语义伪代码，省略对象与错误计数细节：

```text
若允许直接复用短时缓存：复制旧缓存并返回
否则尝试 SPI 读取与条件性 CRC 校验
若读取失败：提前返回，目的数组保持已有值
若读取成功：
    对每个 ready 位有效的源通道 ch：
        destination[channel_map[ch]] = multiplier × signed24_be(received[ch])
    未 ready 的通道不写入
```

其中包含符号扩展、倍率和按映射表写入，没有在该循环跨通道加权或检测心搏。IMU 的 `0x0801EF68` 另有轴组 ready 检查和 `32767 → 32766` 转换，为缺值哨兵留位。CRC属于传输错误检测；不能把它当作波形质量评分。

采样 callback 保存的是当时共享缓存。连续记录相等，既可能表示真实信号没变，也可能表示没有新的转换；0x3c 没有逐点 ready/CRC/replay 掩码可将两者完全区分。五份 ADC 与一份 IMU 按 FIFO 消费配对，不做逐条时间戳相关性匹配。[MCU 原指令审计](../../evidence/analysis/cloud-cleaning-followup/code-only/MCU_PREUPLOAD_CODE_ZH.txt)

## 单点补值与时间边界

遇到符合条件的单点缺口，主机会拿下一点的值填进去。图上虽然补出了一个位置，但缺失时刻真正测到什么仍然不知道。

Frank 的 `0x0021A5C0` 在间隔恰为两个预期步长等条件下标记单缺点。调用方先把当前记录复制到前一个位置，再写入当前位置。以一个不跨秒、符合该分支的合成例子说明：

```text
预期步长：2 ms
输入：tick 100 → 值 10；tick 104 → 值 30
组织后：100 → 10；102 → 30（复制）；104 → 30（当前记录）

102 处没有恢复原测量，也没有计算 (10 + 30) / 2。
```

跨秒时 整秒 epoch 与槽索引的更新顺序另有边界，不能把上面的例子推广为通用修复器。已接受的同秒同槽记录还可能直接覆盖，旧于消费水位的记录可能被跳过；主侧（按缓存分组数量选出的时间参照侧，不表示信号更好）中间空槽可以提前结束并删除整桶。这些操作会改变下游看到的样本集合，判断依据是时间和缓存状态，并非生理信号质量。[主控写值与编码链](../../evidence/analysis/cloud-cleaning-followup/code-only/HOST_PREUPLOAD_CODE_ZH.txt)

编码成功之后还有传输层的取舍：Frank 队列满时拒绝新 body，已排队消息则在发布失败时保留；NATS 流超额的 `discard=old` 又发生在另一层。这些规则不依据心搏、呼吸或信号质量，不能称作生理清洗。旧联合模型中的 `body_candidate` 也不是后续算法确定收到的输入。发布超时与重试只能说明本地状态，不能直接推定远端未保存或已经重复。[发送队列与保留边界](../../evidence/analysis/prepublish-queue-20261108/code-audit/FINDINGS_ZH.txt)

## 双人分离与多通道融合

把左侧和右侧数据放进同一个文件，只是整理数据；分清一段波形属于谁，还需要额外的判断方法。目前查到的上传代码没有提供完整的这部分方法。

已追主控路径将每侧 ADC 8…12 搬到五路 buzzer 压电输出数组，并将四组 IMU 轴数据放到对应数组。左右归并依赖来源侧别、秒键和槽索引。把数据放进一份输出，与判定某个波形属于哪一位使用者，是不同的问题。

| 问题 | 已知输入或机制 | 实际算法尚缺的定义 |
| --- | --- | --- |
| 通道在床上的位置 | 条件性 K60 逻辑映射 | 实体位置、方向、机械耦合和标定 |
| 体动识别 | 压电与 IMU 数组可以作为后续输入 | 使用哪些量、窗口、门限或模型、拒绝掩码 |
| 通道质量选择 | 所审 loader 没有计算质量分数 | 实际使用的质量评分方法、评分和淘汰规则 |
| 同床信号归属 | 左右来源与输出布局已知 | 实际分离器、个体校准和部署分支 |
| 多通道融合 | 已追上传路径保留各通道数组 | 融合时机、权重、对齐与缺通道退化规则 |

有 IMU 不等于必然做了参考消噪；多通道也不能据此推断用了 ICA、PCA、波束形成或某个神经网络。还没有证据把这些方法对应到当前设备实际使用的实现。

## 本地生理处理的审计边界

已经沿着实际接收函数查到了缓存和上传出口，但还没找到从波形一路算出心率或睡眠阶段的完整代码。没有查到这条链，并不等于设备里没有任何算法。

frankenfirmware 的有界审计沿 piezo、ADC、电容等实际接收链追到缓冲、CBOR 和本机 NATS 出口，还没有把“原始波形怎样生成 HR、RR、HRV 或睡眠阶段”这条调用关系完整追通。主机仍存在磁场阈值、连接状态和敲击动作处理，不能因此说“本地无算法”。presence、heartbeat、quality 等词有时描述附件、协议保活或系统库，名称不能替代调用链。[本地生理处理审计](../../evidence/analysis/signal-host/LOCAL_PHYSIOLOGY_AUDIT.txt) · [剩余入口复核](../../evidence/analysis/signal-host/REMAINING_ALGORITHM_ENTRY_AUDIT_ZH.txt)

上述结论只覆盖已追函数和样本，不穷尽所有 stripped ELF、MCU、动态载入或未来版本。姿态、气囊等附件的平均、校准、故障控制也不自动属于床垫实际用于生理判断的处理链，需单独绑定部署。

## App 的输入与本地运算

手机会选取服务器给出的指标、算图表范围并与基准比较。完成这些显示工作，并不能说明手机自己从原始波形算出了指标。

HRV 的日图输入是 rmssd，呼吸率日图是 nemeanRespiratoryRate，心率图是 heartRate。输入已是每时间点一个指标值；没有逐压电通道 SNR、融合权重、剔除掩码或逐搏间隔作为这些图表处理器的输入。App 的 min/max、取整、基准比较属于显示处理，不是从信号重建 RMSSD。[心肺结果链](../../evidence/analysis/android-findings/APP_CARDIORESPIRATORY_PIPELINE_ZH.txt)

健康 DTO 的 value、isAbnormal、dayOfWeekAverage 等字段直接来自 JSON。已追解析链不在本地更新均值或用上下界重新计算异常标志；星期命名也不能证明采用 EMA 或固定七天窗。服务可以接收别处已算出的结果，因此接口位置本身不能排除混合计算架构。[基线代码证据](../../evidence/analysis/cloud-cleaning-followup/code-only/APP_BASELINE_CODE_ZH.txt)

有限历史输出确认 hrv 与 rmssd 是不同序列，且存在有 hrv 无 rmssd 的点。它可以提出质量门控、窗口与输出策略的研究问题，却不能证明 hrv 就是 SDNN，或缺点一定由体动剔除。阶段段长与结果间隔也不直接给出推理窗口。[历史结构](../../evidence/analysis/account-readonly/history-behavior-followup/FINDINGS_ZH.txt)

## HR/RR：结果字段与计算缺口

这里已能查清心率图和呼吸率图分别读取哪个字段。每隔多久出现一个结果，却不能告诉我们内部用了多长的一段波形来计算。

App 心率日图读取 `heartRate`，呼吸日图读取 `nemeanRespiratoryRate`；另一个 `respiratoryRate` 字段不能只按界面名称与其互换。图表处理器收到的是带时间戳的指标数值，已经越过了原始波形到生理事件的转换步骤。

有限历史输出中，心率点通常相隔 300 秒，`nemeanRespiratoryRate` 点相隔 3600 秒。它们描述结果序列的粒度，不能唯一确定检测窗口、重叠步长或内部更新频率。要恢复真正的 HR/RR 链，仍需输入通道、检测事件、拒绝条件、置信度、聚合窗口和结果时间戳定义。

## HRV 1.2.0：字段差异与待恢复参数

两个字段即使出现在同一时刻，数值也可能不同。要解释差别，必须知道之前怎样找心搏、删异常间隔、选择统计时段，单看结果还不够。

已核 App 的 HRV 日图读 `rmssd`；历史响应还有独立的 `hrv`。四段既有会话中，311 个精确时间戳配对的两字段数值均不同，另外 13 个时间点有 hrv 而没有 rmssd。字段区别已有证据，计算区别的原因还没有。

| 需要补齐的变量 | 为什么会影响结果 |
| --- | --- |
| 心搏检测事件与时间基准 | 峰位置误差会改变后续间隔变化量 |
| 有效搏动与异常搏规则 | 决定哪些间隔进入统计 |
| 缺搏、间隔修复方式 | 丢弃、替代或插值会产生不同输入序列 |
| 窗口、重叠与汇总 | 点间隔不能唯一确定一个点使用哪些样本 |
| 两字段的变换和定义 | 相同时间戳不保证相同统计方法 |
| 时间戳锚点 | 可能表示窗口起点、中心或终点，现有材料未定 |

这是需要实际使用的实现回答的问题清单，不是断言这些步骤已按某种方法实现。不能把 `hrv` 擅自解释为 SDNN，也不能将 RMSSD 缺点直接归因于体动剔除。[历史结构证据](../../evidence/analysis/account-readonly/history-behavior-followup/FINDINGS_ZH.txt)

## 在床 3.2.1 与分期 0.1.1：输出契约与实现缺口

已知手机能显示哪些睡眠标签，以及怎样缩短首尾显示。真正把传感读数判断成这些标签的规则或模型，仍缺实现材料。

客户端阶段字段约定包含 `awake / rem / light / deep / out` 和每段时长。这证明客户端理解这些输出，不证明生产者是单个五分类网络，也不证明 out 与其余四类来自同一模型。

已恢复的 mapper 将首尾符合条件的 awake/out 段限制到 600 秒。这是显示数据修剪，没有由此统一重算 session.duration、阶段汇总与评分。107 段历史正整数时长的公约数为 30 秒，同样不足以证明实际使用的模型固定按 30 秒 epoch 推理。

```text
生产者尚缺：原始信号 → 特征/embedding → 在床与睡眠判断 → 平滑/合并 → 阶段
已见消费者：阶段标签与时长 → 数据映射 → 首尾显示裁剪 → 图表与阶段分布
```

真正需要追的是输入模态、特征维度、窗口、推理步长、模型或规则、阈值、个体适配、时序平滑和会话切分。用户修改睡眠时间的 API 是另一个输入入口，不等于取得了这些运算。准确的阶段映射、聚合与编辑规则见 [结果与分期详解](../algorithms/results-and-staging.md)。

## 基线、异常判定与睡眠评分

页面里的“与你平时相比”和“是否异常”，有些直接来自服务器字段。手机把它们显示出来，并不代表它重新算过这些基准和分数。

基线 DTO 包含 `value`、`isAbnormal`、`dayOfWeekAverage`、`dayOfWeekStdDev`、`dayOfWeekDeviation`、`abnormalLowerBound`、`abnormalUpperBound`、`probability`。已追解析链直接读取这些字段，不是手机用上下界重新计算 isAbnormal，也不能由 dayOfWeek 推定某个 EMA 或固定七天窗。

SFS、SQS、SRS 同样需要区分服务给定分数与手机做的显示、差值和分布。后者存在可写成公式的本地操作，但不提供后台评分目标函数。[App 指标、阶段、评分和健康处理的详细公式](../algorithms/results-and-staging.md)

## 算法版本与部署对应

版本号能帮助区分不同发布版本，但它本身不包含计算规则。还需要把这个编号对应到具体程序或模型文件，才能继续拆解。

历史 session 的 `0.1.1 / 3.2.1 / 1.2.0` 是 sleep、presence、HRV 三种命名版本。尚无官方资料把它们映射到程序、模型 hash、权重或发布清单。顶层 v3、sfsCalculator v3.2、设备 firmwareCommit、SWU rat_version、MCU 版本属于不同版本命名空间。

已查官方范围的历史 batching、相关论文与研究仓库可以提供研究背景，但没有生产版本交叉对应。没有输入代码或模型，单独几个版本字符串无法恢复滤波系数、网络结构或训练集。[版本谱系审计](../../evidence/analysis/account-readonly/version-lineage-followup/FINDINGS_ZH.txt)

## 后续材料与验收标准

优先补齐能把“原始输入、处理过程、最终结果”连起来的材料。每一项都要能指出具体代码或可验证记录，不能只凭结果长得像就算完成。

- ALG-01：先取得“字段名＋版本值→程序或模型摘要”的原厂清单和部署物，再从真实入口追滤波、质量、融合、推理及输出；验收要求具体函数、参数和版本绑定。
- ALG-02：在有原始波形及通道标定后，建立带来源、同步和有效性标记的离线数据集，量化本地补点/重放；没有真实输入时不宣称测得生产误差。
- ALG-03：取得有版本绑定的特征、逐搏间期或处理日志，解释 hrv/RMSSD 分歧与缺值；仅用输出拟合出的候选需标为实验假设。
- ALG-04：补齐评分、基线、异常与分期后处理的官方实现或可验证日志，明确窗口、状态更新和汇总规则；不以 UI 阈值冒充后台公式。
