# 手机端实际计算：指标、潮热、午睡与时差计划

这份国行 APK 的已查主链从服务器指标、状态或用户设置开始。手机会做统计、日期分组、缓存与显示计算；这些实现不能补出原始波形到 HRV、在床和分期的生产算法。

## 健康指标：取值、汇总和明细不完全相同

首页异常提示实际读取服务端 HR/HRV/呼吸的异常值；概率、标准差等字段虽在模型中存在，直接引用搜索没有找到相应业务计算。存在字段或选择器，不等于实际页面一定调用。

半年/全年异常趋势另取一份周聚合，按 `HR异常数 + HRV异常数 + 呼吸异常数` 选出计数最多的样本，同分保留先出现者。但输出总数仍来自当前输入样本，明细可来自选中的那一天。两者并非必定同一层级，不能用总数反推每一天的异常判断。

## 潮热：图表总和为什么可能不同

| 输出 | 本地取数方式 |
| --- | --- |
| 周图 | 只取日期窗口内样本，同日后值覆盖前值，缺日填 0，每点取整 |
| total | 遍历整份 aggregate.samples，先求和再取整，未复用日期过滤和去重结果 |
| 当日次数、平均时长、常见阶段 | 使用服务端日摘要；不在此重新识别潮热事件 |

如果输入包含窗口外样本、重复日期或小数，图点之和与 total 可以不同。这里是代码允许的结果，并未观察到账号实际返回这些情况。

设置存入 Room，缓存有效期 12 小时。激活前会乐观更新界面：当前阶段温度加设置偏移，raw 档位限制在 −100..100；随后调用独立的 activate API。停止也有独立 API。这两条已查按钮链没有经过普通调温的 Backup BLE 路由，不能把普通 BLE 调温能力直接套过去。

## 午睡：配置、激活和倒计时是三件事

开始流程先提交午睡闹钟配置，成功后再提交温度/时长的激活请求。请求成功后保存设置，显示状态的 start/end 则取自服务器响应。这不是一个原子事务，也不是手机自己判定已经入睡。

延长默认 10 分钟，停止调用 deactivate。状态查询收到 404，以及延长/停止收到指定的 NoActiveNapException 时，会清除本地状态；一般网络失败不能一概解释为已经停止。

倒计时每秒用手机当前时间重算：

```text
total = end − start
remaining = end − 手机当前时间
progress = trunc((total − remaining) / total × 100)  // total>0
```

该方法未将进度限制在 0..100。`remaining<=0` 时直接结束显示循环，没有在这一分支调用停止、刷新或关闭 banner。因此“手机显示倒计时结束”不能作为设备停止控制的证据。

## 时差计划：方案生成与本地任务处理

App 提交行程与计划请求，服务器返回已经包含类型、时间、阶段、说明和状态的任务。手机按以下规则组织它们：

| 阶段 | 本地分组 |
| --- | --- |
| 飞行前 | 按日期升序，组内保留输入顺序 |
| 飞行中 | 按航段 ID 首次出现顺序分组，组内保留输入顺序 |
| 到达后 | 遇到 SLEEP 任务结束一组；未遇 SLEEP 的尾组在该函数中不另行提交 |

“当前任务”是整个遍历中的第一个未过时任务，至多一个；没有另做最近时间排序。单组完成率为 `已完成数 / 总任务数`。点击完成先改 Room，再请求服务端；失败时反转状态，不是恢复完整旧数据快照。

时间也有实际代码细节：`Ga/s.n(offset)` 先取手机时区的墙钟日期/时间，再用指定 offset 重新解释成 Instant，不能当作保持同一时刻的普通时区转换。详情页还存在 `Ga/s.equals(LocalDate)` 的类型不匹配比较；首页卡片使用另一条 LocalDate 比较链，不能把两者的行为混为一谈。

草稿日期/时刻修改、航班映射、结束/删除行程、首页摘要与国行通知显示/点击入口已继续补齐。通用推送链已恢复，但缺少实际 Jetlag 消息 payload，尚未将某个时差任务绑定到具体通知交付。光照、睡眠或补充剂时间安排的服务端生成策略仍缺实现。
