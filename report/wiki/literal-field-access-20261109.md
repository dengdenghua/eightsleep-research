# nonUSB 字面量偏移字段图与空洞绑定判定

相关实现见[上报对象构造链与 0x3e28 布局分区图](report-object-layout-20261109.md)、[GPIO 描述表、0x10f0 块字段与调用图](post-layout-closure-20261109.md)与[调用目标闭合与 trampoline 簇](residual-target-closure-20261109.md)。本章把字段访问的识别从伪 C 的 `param_2 + 0xNNN` 扩展到指令级的字面量偏移寻址，并给出空洞见证的绑定判据与 trampoline 簇的分支链解码。

分支归属见[五态帧解析状态机与 0x08016fdc 跳转表归属](state-machine-switch-closure-20261109.md)：真正的 switch 在 `08016fd8`，五项跳转表位于 `08016fdc`，本章记录的六组「字面量装载 + 调用」属于序列化冷路径与普通调用点，不是 switch 分支。

全部结论来自冻结 BBIN 的只读字节与既有 Ghidra 工程的 `-readOnly -noanalysis` 导出；本主题没有新增 Ghidra 调用。没有执行固件、没有联网、没有访问设备或账号。覆盖率不变，字段语义与分支归属的其余部分仍需材料或设备。

## 适用范围与计数口径

字段台账包含不同构建及同一函数的重复导出，并按文件路径归组。 2609 条、114 组与 68 组是候选检索统计，不是已确认的独立字段访问或函数绑定数量。逐位点字节复核与共享 writer 的路径语义见[字段访问的镜像绑定](field-site-binding-20261109.md)。该模型仅用于候选检索，不能单独证明主对象空洞闭合。`0x1c08` 的对象、计数和门限见[主循环控制流](main-object-control-20261109.md)。

## 为什么伪 C 提取会漏掉字段

主分派的字段写法是伪 C 里的 `param_2 + 0xNNN`，而同一对象在别的函数里是这么访问的：

```asm
ldr  r3,[0x080161f4]   ; 字面量值 = 0x1c08，就是字段偏移
ldrb r3,[r7,r3]        ; r7 是对象基址
```

偏移在 literal pool 里、基址在另一个寄存器里，伪 C 中根本不出现 `param_2`。只扫伪 C 会产生假阴性，例如 `0x1c08` 的字面量偏移访问。

提取规则：字面量值 `< 0x3e88`（对象尺寸下界）才可能是字段偏移；其后 400 字符内必须出现 `[base,rX]` 且 `rX` 与装载寄存器同名；按紧随指令的 `ldr`/`str` 判读写。该文本规则得到 224 个候选偏移；是否属于同构件、寄存器是否仍保持其值，以及消费者真实读写方向，都须由字节与值流分别核实。

## 偏移相同与对象身份的区别

只看偏移值不够：同一个数值可以是任何对象的字段偏移。`0x24d` / `0x24e` 在 4 个函数里出现：

```
report-object-layout/pass1/08019bac.txt
local-tmag-closure/pass4/08023958.txt
local-sensor-recovery-followup/pass2/080224f0.txt
post-layout-closure/pass6/08018744.txt
```

这些数值相同的偏移不能直接当作主对象窗口的见证；应分别看候选筛选和真实基址关系：

1. **候选筛选**：这四份导出没有满足至少两个已覆盖偏移的启发式；这只能用于排序，不能独立证明它们操作别的对象。
2. **基址证据**：`08019bac` 的 `0x250` 块在主对象里的基址是 **`0x3b48`**，块内偏移 `0x24c/0x24d/0x24e` 对应主对象的 **`0x3d94 / 0x3d95 / 0x3d96`**，与 `0x0234..0x0258` 无关。其中 ID 字节 `0x3d94` 落在已覆盖区间 `[0x3b48, 0x3d98)` 内，进一步说明它不属于该空洞。

`0234..0258` 的候选材料中， `callsites.asm.txt` 两条记录实际重复指向同一个 USB 相容的 `0x24d` 位点，不匹配冻结 g0；其“同文件包含多个偏移”的启发式不能证明同一个对象。

所以「有候选」和「有见证」是两回事。原台账里每个空洞同时记录 `candidate_accesses` 与 `bound_accesses`，被拒绝的绑定连同理由写进 `rejected_binding` 段。

## 候选窗口与当前边界

| 空洞 | 字节 | 候选访问 | 已绑定访问 | 判定 |
| --- | --- | --- | --- | --- |
| `0234..0258` | 36 | 10 | 原判 2，实际重复且不匹配 g0 | 主对象待绑定 |
| `027c..02a0` | 36 | 1 | 0 | 无见证（唯一候选 `0x029e` 未绑定） |
| `1c08..1c0c` | 4 | 7 | 六条匹配 g0，去重四个位点 | 主循环相对访问已核；绑定依赖调用者与正常寄存器保存 |
| `3e01..3e08` | 7 | 0 | 0 | 无见证（连候选都没有） |

上表为候选检索统计，主对象绑定以逐位点字节核验为准；12/14 与 43B 不作为已验收的对象绑定或缺口总量。

「见证」的含义限定为**该偏移在某个已绑定函数里被当作字段使用**，即类型级字段证据；它不是「主对象实例的该字节被写」，也不要求实例同一。

## trampoline 簇是分支链

按原始字节分类，真正的 `switch` 位于 `08016fd8`，五项跳转表从 `08016fdc` 开始，指向五个状态处理块。本节的六组「字面量装载 + 调用」不是 `switch` 分支；前四组是序列化默认值的冷路径，后两组是普通调用点。五个状态处理块与帧格式见[五态帧解析状态机与 0x08016fdc 跳转表归属](state-machine-switch-closure-20261109.md)。

区间 `[08015e00, 08017000)` 共 496 条指令，其中 6 组「字面量装载 + 紧随调用」：

| 位置 | 寄存器 | 字面量地址 | 值 | 调用目标 |
| --- | --- | --- | --- | --- |
| `08016142` | r0 | `080161e8` | `0x080252a8` | `08012754`（日志） |
| `08016e02` | r1 | `08016f8c` | `0xbf800000` | `08015f08` |
| `08016e08` | r0 | `08016f90` | `0xff7fffff` | `08015f28` |
| `08016e0e` | r0 | `08016f90` | `0xff7fffff` | `08015f46` |
| `08016e14` | r1 | `08016f90` | `0xff7fffff` | `08015f64` |
| `08016f18` | r0 | `08016fc4` | `0x2000a498` | `080134be` |

值的可读语义：`0xbf800000` 按小端 IEEE754 读是 **-1.0f**（无效值哨兵）；`0xff7fffff` 取反得 `0x00800000`，即**清第 23 位**的掩码；`0x080252a8` 指向冻结镜像里的字符串「`[sensor] unshielding took %ums before settling time start`」。

四组连续分支（`08016e02/08/0e/14`）把 -1.0f 与清位掩码交给 stub，形态上是故障/状态清除路径；`08016142` 那组把格式串交给日志函数，说明同一区域还承担诊断文本格式化（栈缓冲在 `sp+0x20`）。派发门控是 `08016e1a` 的 `cmp r2,#0` / `beq 08016e22`：**r2 为 0 时跳过 `08016e1e` 的调用**。

每个分支属于哪个 `switch` 的哪个分支仍未解析，需要把派发器的跳转表与调用点绑定。

## 边界

1. **覆盖率不变**：11297/15880 = 71.14%，空洞字节仍不计入覆盖。
2. **两个空洞（43B）仍无见证**。
3. **绑定判据是启发式**：≥2 个已覆盖偏移只是「同一布局」的强提示，不是形式化证明；判据本身随台账交付，可被反驳和替换。
4. **trampoline 簇的分支归属未解析**。
5. **169 个大函数内部地址**仍无函数体，需重新反汇编，越只读边界。

本章不做：不执行固件、不做动态验证、不接设备、不访问账号或网络；不修改 Ghidra 工程、不重新反汇编、不新增指令；不把字段证据算成覆盖率提升。41 项字节核验与 28 条模型断言全部通过，两组独立计数在 2609 访问、224 偏移、68 绑定函数、2 个闭合空洞、6 组配对上互相吻合。
