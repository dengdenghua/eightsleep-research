# Frank 发布前队列：容量、丢弃与重试

补齐的是 CBOR 编码完成后、进入本机 NATS 前的发送队列。原来的 34 场景主控模型止于 `body_candidate`，不能代表后续消息已经发出。此次结果来自同一 MTK 固件的静态代码和独立合成模型，没有实机采集。

## 数据到达哪一步才算成功

| 阶段 | 已能确认的事情 | 还不能推出 |
| --- | --- | --- |
| 编码完成 | 主控生成待提交的 CBOR 正文 | 消息已进入发送队列 |
| Frank 入队成功 | subject 和 body 已复制到进程内队列 | NATS 已收到，或已保存到磁盘 |
| `js_Publish` 返回 0 | worker 按发布成功路径出队、释放正文并轮转 | 独立观测到了网络 ACK，或云端算法已拿到数据 |
| uploader 收到云端批次确认 | 对应上传协议层的确认逻辑已执行 | 睡眠算法已完成处理，或所有样本都可下载 |

主控输入已经被消费、logger 计数增加、Frank 入队成功、NATS 发布成功、云端批次确认是不同事件。不能共用一个“上传成功”标记。

## 实际容量和行为

| 队列 | 有效容量 | 已确认的用途 |
| --- | --- | --- |
| 原始数据 JS 队列 | 16 条消息 | Stealth、Piezo、健康状态等共享 |
| raw.log JS 队列 | 1,024 条消息 | `mask=1` 的日志提交 |
| raw.events.* JS 队列 | 32 条消息 | 事件提交 |
| core 队列 | 16 条消息 | 已确认包含 Frank heartbeat；不声称只有它 |

这些是消息条数，不是采样点数、字节限额或固定缓存秒数。环形队列另外保留一个空槽；消息正文单独分配内存。

- **队列满：** 拒绝新消息，旧消息保留。已审计的 raw 提交函数记错误、释放临时正文并推进自身计数；该正常返回分支不重试提交。
- **已经入队但发送失败：** 保留队首，重建连接，执行约 1 秒等待后重新调度。1 秒不是严格重试周期。
- **发布返回成功：** 释放该条正文和主题，读位置前进，再轮转到下一个 JS 队列。
- **调度：** core 优先，其后还有 KV 状态协调。JS 从当前轮转位置重新扫描；失败不会永久锁住一个队列指针，但在特定持续积压条件下会推迟后续队列。
- **停止：** worker 在循环顶部检查运行标志，已审计停止路径没有排空队列。后续已补 main 正常停止、线程包装析构与异常表，见[系统分析](system-deepening-20261108.md)；任意间接回调及全系统补偿保存仍不作全称断言。

Frank 的“满时拒新”与后续 NATS `raw_mem` 的“超额淘汰旧消息”分别发生在两个位置。仅观察到序号缺口，不能直接判定是哪一层丢弃。

## 模拟验证和限制

10 个指定场景覆盖满队列拒新、不同 raw 类型共享容量、正文复制与回绕、连续发送失败、恢复、轮转、core 优先、ACK 不确定情景及运行标志退出。另用独立 `deque` 对照 1,024 条操作序列、共 8,192 步。

模型使用合成正文，省略 KV 协调；不覆盖分配异常、并发交错、库内部协议、完整析构和真实吞吐。一次发布失败后再次尝试，不证明服务端实际重复落库。场景中关于 ACK 丢失或远端已接收的标签是显式假设。
