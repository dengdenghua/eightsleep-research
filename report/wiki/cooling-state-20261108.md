# 冷却上限如何随时间变化

已恢复 Frozen 1.7.7 的正常冷却自适应状态，入口为 `0801BB28`。25个有限场景核对了时间边界、滞回、上限累加与两种重置；这些是静态分支推导的模型对照，尚未在实机运行。

## 从限制制冷到放宽上限

normal Pod6 配置初始上限0.67，误差为目标减水温。温差满足冷却门控时，代码记录历史最佳绝对误差；只有 `float32(best−0.1) > abs(error)` 才算改善。恰等于浮点计算后的边界不更新进展计时。

180秒没有达到上述改善，代码才检查此前是否触发过限幅。此前触发过则进入放宽状态；没有触发过则只记 suppressed 提示。本步的限幅判断发生在这个检查之后，因此第一次在180秒后裁剪，不会在同一次调用立即进入放宽状态。

进入放宽状态后，每隔至少30秒的一次调用将上限增加0.11，最大1.0；迟到多个周期也只增加一次。温差改善会更新最佳值和进展计时，但不清除已经进入的放宽状态，改善与递增可以在同一次调用发生。

| 调用时间示例 | 无改善且此前触发过限幅时 |
| --- | --- |
| 179999 ms | 尚未进入放宽状态 |
| 180000 ms | 进入放宽状态，上限仍为约0.67 |
| 209999 ms | 尚未到首次递增 |
| 210000 ms | 上限增加到约0.78 |
| 下一次迟至360000 ms | 只再增加一次，约0.89；不追补漏过的周期 |

这里假定起点为0且相关分支持续满足，实际调用时间取决于调度。上限1.0意味着本层不再裁剪，后级环境限幅与执行器保护仍各自运行。

## 限幅显示不等于实际裁剪

限幅 engaged 状态带0.05滞回。例如上限0.67、此前已 engaged，需求−0.64时仍可保持 engaged，但需求没有小于−0.67，本步不裁剪。实际裁剪标志独立决定调用方是否回退积分，不能用显示状态替代。

## 启停和改目标清掉的状态不同

| 操作 | 已核重置规则 |
| --- | --- |
| 停用 | TEC请求与两处输出快照清零，未执行完整冷却状态重置 |
| 同目标再次启用 | 清最佳误差、进展计时和部分标志，保留放宽状态及自适应上限 |
| 请求目标改变 | 另清放宽状态，上限恢复base，重置递增计时 |
| 误差回到门控外或disabled旁路 | 本步不裁剪，清进展相关状态，保留放宽状态及上限 |

启用同时改变目标时，后续目标变化重置仍会执行。跨当前水温且目标变化大于5°C还会走独立PID重置；它与冷却状态重置不能混为一项。此处只解释所列enable/target入口，尚未将所有设备mode写入者归并验证。
