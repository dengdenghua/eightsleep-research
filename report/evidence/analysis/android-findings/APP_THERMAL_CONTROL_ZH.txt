三、整数档位、App 显示温度和设备水温必须分开

Ga.b.a 是发送的原始整数档位。LEVEL 显示以 raw/10 为基础，整数显示使用 sign(raw/10)×round(abs(raw/10))。
METRIC 分支先把 raw 钳到 [-100,100]，再用分段线性函数：
  raw < -90：13 + (raw+100)×3.2/10
  -90 <= raw < 0：16.2 + (raw+90)×10.8/90
  raw >= 0：27 + raw×17/100
IMPERIAL 分别为 55+(raw+100)×6.2/10；61.2+(raw+90)×19.4/90；80.6+raw×29.4/100。
因此 raw -100/-90/0/100 对应 App 摄氏刻度 13/16.2/27/44，华氏刻度 55/61.2/80.6/110。两个刻度是分别写死的映射，不应用精确 C↔F 恒等式替换原代码。
Ga.b.g 对显示整数做逆向转换，e/f 增减显示值再限制原始档位范围；构造本身仍可接收任意 int，不能据此宣称网络层已验证所有越界输入。
证据：J/Ga/a.java:13–26，J/Ga/b.java:19–169；Smali S2/Ga/b.smali:31–264，含常数和乘除顺序。[temperature-level-type, temperature-enum-map, smali-unit-conversion-a, smali-unit-conversion-b]

这证明的是 App 的显示/输入转换。不能把 App 的 13–44°C 刻度直接替代此前固件 Frank 普通温控目标映射，更不能当成床面或水温实测范围。云端可能进一步转换，当前未获得服务器实现。

四、Backup BLE 条件、命令和成功后处理

主分支：C0 只有在 BLE command 可构造、device 存在且 Qb.u.b() 为 true 时直接走 H0.c。
u.b() = device.supportsOfflineCommands && 当前计算的 SystemStatus != NORMAL。
u.c() 综合强制 offline/outage、功能开关、设备在线和服务状态，可能返回 DEVICE_OFFLINE、OUTAGE、PHONE_OFFLINE、POOR_CONNECTION；不能简单写成“手机没网就一定可用”。
正常云路径失败后 y0 检查 BLE command 存在且 u.a()，才 fallback；u.a() 还要求设备支持及 offline/outage/phoneOffline 对应开关之一。
证据：J/Qb/u.java:51–79，J/Qb/g.java:52–53，J/p284ld/C0.java:41–73，J/p284ld/C3931y0.java:61–78；Smali S2/ld/C0.smali:131–241、S2/Qb/u.smali:107–134。[hardware-path-state, device-backup-support-state, temperature-api-or-ble, temperature-ble-fallback, smali-backup-path, smali-backup-state-gate]

BLE 温控 characteristic UUID：[ID_REDACTED]；WriteType.WithResponse。
请求 DTO 为 {name, value}。真实 name 从 Smali 字段注解得出：
  LEFT / RIGHT / SOLO → leftLevel / rightLevel / soloLevel

五、日程和三段偏好传什么

SmartTemperatureNetworkModelJsonAdapter.toJson 明确输出 bedTimeLevel、initialSleepLevel、finalSleepLevel 三个 int，对应域内 bedTime/night/morning。
TemperatureSettingsRequest 的 smart 字段持有这个对象。[smart-temperature-adapter: J/com/eightsleep/data_core/data/model/SmartTemperatureNetworkModelJsonAdapter.java:76–88]
这是三段设定值的 wire schema；不是生理睡眠阶段分类器，不能将 initial/final 解读成模型的 NREM/REM 输出。

BedtimeUpdateRepository.updateBedtimeTemperature 从缓存日程列表找目标 id，更新对应 device type 的原始档位，再 PUT v1/users/{USER_ID}/bedtime。
请求 schedules[] 每项为 id/enabled/time/days/startSettings；startSettings 可含 elevationPreset、bedtime、pillowBedtime、audioSettings。
bedtime/pillowBedtime 均从 Ga.b.a 原值取得。days 用 DayOfWeek.toString().toLowerCase(Locale.ROOT)，time 经注册 LocalTimeAdapter 输出 ISO_LOCAL_TIME。
响应 schedules 转实体写 Room。这里证明了客户端上传与本地缓存，未建立其与 native TemperatureScheduler 的直接调用；不能用此前 calendar stub 的结果否定云日程功能。
证据：J/BedtimeUpdateRepository.java:20–30,115–165；T9/a.java:6–7；U9/d.java:49–51；BedtimeScheduleRequest.java:6–21；BedtimeScheduleStartSettingsRequest.java:6–16；LocalTimeAdapter.java:38–43；ce/C2685l.java:1781。
Smali T9/a.smali:38–65 复核 PUT 路由。[bedtime-repo, bedtime-api, bedtime-request-call, bedtime-request, bedtime-start-request, schedule-time-serializer, time-serializer-registration, smali-bedtime-api]

八、读取状态与缓存为何不能当作传感实测结果

云 DeviceTemperatureSettingsResponse.currentLevel/currentDeviceLevel/currentState/smart 经过 toDomain 映射，currentDeviceLevel 为 null 时用 0；gd/q0 按 device specialization 选择响应，并缓存日程和该设备温控结果。
BLE ReadPodTemperature DTO 含 heatLevelL/R、tgHeatLevelL/R（字符串）和 activeL/R。
currentLevel()/targetLevel() 对所选侧字符串转 int，解析失败返回 0；ld/C3908m0 以 target 更新目标档位，以 current 更新设备档位，active true/false 映射 SMART/OFF，合并到同一 TemperatureRepository map。
证据：DeviceTemperatureSettingsResponse.java:131–150；p162gd/q0.java:52–80；PodTemperatureBluetoothResponse.java:88–101,143–161；p284ld/C3908m0.java:81–120；p284ld/C3914p0.java:49–76。
[temperature-response-domain, temperature-response-cache, ble-temperature-current-level, ble-temperature-reply, ble-temperature-reply-cache, ble-temperature-read-usecase]
这类状态可能来自云响应、BLE 读取或写后乐观更新；SMART 是温控状态，字符串解析默认 0 也不是传感器测得零度。未抓真实响应，不能宣称某次设备动作已完成。
