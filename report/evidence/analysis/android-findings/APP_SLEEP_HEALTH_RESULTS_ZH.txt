3. health 的 wire schema 与数值来源

DailyTrendsResponse.health 可空；HealthScoreResponse 的 breathing、heartbeat、wellbeing 三项也可空。breathing/heartbeat 的 HealthScoreStatResponse 必须具备 value(double)、rating、ranges、timeseries；生成 adapter 对四项缺失/null 抛错，timeseries 本身可为空列表。[H07,H08,H11,H19]

HealthScoreStatTimeseriesEntryJsonAdapter.fromJson 是有序的二元 JSON 数组：beginArray → nextString → Instant adapter → nextDouble → endArray。即 ["时间字符串", 数值]。这与上轮 HR 的 MetricPoint 自定义读法不同，不能套同一解析器。它的 toJson 也写数组。ce/l.m3 把该 adapter 加进 Moshi 注册集合，已核对生产配置。[J/com/eightsleep/data_metrics/data/adapters/HealthScoreStatTimeseriesEntryJsonAdapter.java:7–27；对应 S/…smali:41–99；S/ce/l.smali:8472–8509；H06,H34,H41]

rating 的枚举 wire 名经 Smali 注解核实为 inRange / outOfRange / unknown；这里的 UNKNOWN 是明确枚举值，不据此声称任意未识别字符串都会自动回退。ranges 有 inRange / outOfRange，子范围 min/max 为可空 Integer；本轮已追的详细图阈值路径并不读取这些返回范围。[H14,H27,H44]

HealthScoreStatResponse.toDomain:99–108 透传 value/rating/ranges，映射各 timeseries 项；RawHealthScoreStat.a:29–37 做显示模型转换而不重新计算健康分值。RawHealthScoreStatTimeSeriesEntry.withDisplaySettings:67–69 将同一 Instant 和 ClockSystem 包进 Ga.s，value 不变；Ga.s(Instant,ClockSystem):234–240 保留 Instant，ClockSystem 是显示时钟制式，不是重采样或推理。[H07,H18,H56,H65]

wellbeing 的必要字段为 value、rating、ranges、abnormalities、dayCount、daysUntilAvailable、daysUntilCalibrated；toDomain:136–137 七项透传给 rc/m。该转换没有根据 HR/HRV/RR 在手机重算 wellbeing。[H35,H36,H47]

4. 干扰日图：实际小时分组、求和、边界

HeartbeatDisturbancesMetricDataProcessor 与 BreathingDisturbancesMetricDataProcessor 的完整 transformDayData 已逐段读 Smali。[S/…/HeartbeatDisturbancesMetricDataProcessor.smali:76–421；Breathing…smali:76–423；H23–H26]

共同操作：
  a. 通过 P2.a.P(dailyTrends, selectedSessionId) 选择 Session，取 Session.e 起点和 Session.t duration；缺起点/Session 则返回 null。
  b. hours = ChronoUnit.HOURS.between(start.Instant, start.plusMillis(duration.toMillis()).Instant)。这是完整小时数量，末尾不足一小时不再生成一个桶。
  c. heartbeat 读取 DailyTrends.L.b.timeseries，breathing 读取 L.a.timeseries。遍历整个选中的日级健康 timeseries，按各点 Instant 经 Ya.d.f 的 getHour() 分组；该 key 只有 0–23，没有日期。
  d. 对 i = 0…hours−1，输出时间为 start + i 小时，以该时刻的本地小时查组，把组内所有 value(double) 相加。没有这一小时的组、健康字段缺失或列表为空，sum 都走 0.0。
  e. heartbeat 构造 wg/q(sum, sum<=3.0, time)；breathing 构造 wg/p(sum, sum<=14.0, time)。这是显示数据/布尔标记，不是原始信号检测。

时区细节：分组用 Ya/C2102d.f:68–74 的 ZoneId.systemDefault()；输出 lookup 在 heartbeat 用 Ga.s.l:167–174、breathing 再用 Ya.d.f，二者也都取 systemDefault。它们不是直接按 Session.timezone 分组。[H32,H33]
在上述方法范围内，没有按 selectedSession 的完整起止区间过滤健康序列，也没有以日期+小时作 key。Session 选择改变输出起点和桶数，不改变输入为日级 health 的事实。

静态语义算例（不是实包、不是执行 App）：若起点 23:30、时长 2 小时 30 分，则输出桶时间只有 23:30 与次日 00:30；同一本地 23 点的 23:05 与 23:55 两个输入点都会被归入 key=23。若响应含不同日期的相同小时，它们也会落在同一个组。真实服务是否总是提供已裁剪且唯一日期的序列未知，故此处不是实机错误复现结论。

单位边界：资源 breathing_disturbances_rate_format 为 “%.1f /h”（中文“每小时%.1f次”），heartbeat_disturbances_rate_format 为 “%.1f %%”。因此不能把心搏数值 3 或被求和的 double 一概叫作“3 次心搏事件”。本报告只记录代码阈值及产品显示单位，不作临床解释。[H54；values/strings.xml:781,1874；values-zh-rCN/strings.xml:769,1832]

期间图的规则另有差异：transformPeriodData 从服务聚合 Sample.double map 直接选 HEARTBEAT 或 BREATHING，仍比较 <=3 / <=14；缺值则保留 null，不像日图缺小时变 0。没有从期间原始波形重新识别干扰。[H67；Heartbeat…smali:423–491，Breathing…smali:425–493]

5. headline、健康卡片和等待状态并非同一种判断

详细图 ViewModel.packageMetricData 用当前日期 DailyTrends.health 对应 value 作 primary，用 AggregatePeriod.doubleAvg[对应类型] 作 secondary；primaryGood 是 primary<=3 或 <=14。它不与 secondary 作比较，也不以返回 rating/ranges 决定这一个布尔值。health/字段不存在则 primary 和 primaryGood 为 null。[H15,H16,H66,H68,H69；HeartbeatViewModel.smali:269–347；Breathing…:258–336]

健康摘要卡片 P2.D.u(rc/a) 则直接用各项的 rating==IN_RANGE 构造 wg/G；UNKNOWN 与 OUT_OF_RANGE 在此比较均为 false。缺字段不构造对应项；数组交给 Im.n.h0。MetricsHomeViewModel$updateContentView$1$2.smali:1101–1155 真正调用该 helper，并对结果 stats.isEmpty 做分支。因此“健康首页颜色”不能笼统归结为详细图的 3/14 阈值。[H30,H43,H52；S1/P2/D.smali:8175–8283]

HealthCheckHomeViewModel.updateContent$lambda$12 还会对返回 value 选本地文案：呼吸依次判断 0、<10、<=14、其余；心搏依次判断 0、<2、<3、==3、其余。对应标尺参数分别为 10/14/31 与 2/3/12。这是 UI 层分档和标尺，不是已恢复的服务器 health 分类算法。
精确细节：呼吸标题的 10/14 比较前存在 double→float→double，推荐文案分支直接比较 double；非常接近界值时不可把两段强行写成完全相同函数。[H40,H57–H59；HealthCheckHomeViewModel.smali:2911–3472]

wellbeing 等待状态有真实消费者：updateContent.smali:1999–2063 读取 rc/m.f（daysUntilAvailable），与 0 比较，>0 时构造 wg/N(daysUntilAvailable)，其 toString 明确 Pending(daysUntilAvailable=…)。该计数由服务器 DTO 透传，不能把它写成手机根据信号质量自行训练或判断已校准；daysUntilCalibrated 虽保存在模型中，本轮未把它的所有 UI 消费者闭环。[H46,H47,H55]

缺数据边界必须分开：有效 Session + 缺 health 在日图 processor 内可生成 sum=0，但 headline 仍可 null。Ag/b0.smali:528–565 对 DAY 且 primary 非 null 才构造一个附加日视图 lambda，主图 lambda 在:618–628 另行构造。本轮未穷尽公共 Compose 容器所有显示/遮罩分支，不能声称这些 0 一定出现在真实屏幕上；也不能仅由 headline 为 null 推断所有图形都被隐藏。[H42,H48,H49]
以上是字段可用性、时间桶和显示状态，没有恢复与 Pod6 多通道 ADC 绑定的 SNR、通道权重、传感器置信度门限或质量融合规则。

6. 打鼾：服务器分段、手机时间累计和期间减法

SessionResponse.snoring 是可空 List<SnoringResponse>，每项需要 intensity 与 duration(int)。enum wire 名为 none/light/medium/heavy；MEDIUM 和 LIGHT 的 labelResId 相同。toDomain 将 duration 按秒转 Duration；SessionResponse.toDomain:356–365 把缺列表转空列表，保留每项强度，不在此重新检测打鼾。[H12,H13,H22,H29,H45]

SnoringMetricDataProcessor.transformDayData 取被选 Session.k 与 Session.e，交给 Tb.a.m0。m0 的第一个片段从 Session 起点开始；后续片段 start=前一片段 start+duration。输出 intensity/duration 保留，日片段 percent 字段统一为 0.0。响应每项没有在这个 DTO 中携带独立绝对 timestamp，日图由顺序与时长重建连续时间；不能把 UI 重建时间当成设备原始检测时间戳。[H09,H17,H34；S/Tb/a.smali:7598–7713；SnoringMetricDataProcessor.smali:73–126]

期间图只取聚合值：SNORE、SNORE_PERCENT、SNORE_HEAVY、SNORE_HEAVY_PERCENT。duration 缺失默认 ZERO，比例缺失默认 0；百分数除 100。构造 LIGHT duration=总量−HEAVY，LIGHT fraction=总比例−HEAVY比例，另外保留 HEAVY。该方法没有在减法后 clamp，所以不能先假设不一致响应一定被修正；本轮没有真实不一致响应。[H37；SnoringMetricDataProcessor.smali:128–295]

SnoringViewModel 当前 summary duration 来自 DailyTrends.sleepQualityScore.snoringDurationSeconds.current，非累计日图片段；DAY 基线取该 metric.inclusive7DayAverage，其他周期取 AggregatePeriod.durationAvg[SNORE]，缺基线默认 ZERO。
summary snore fraction 来自 DailyTrends.snorePercent/100，period 比例来自 AggregatePeriod.doubleAvg[SNORE_PERCENT]/100；本地 primaryGood 比较 fraction<=0.1。这个 10% 是显示比较值，不是音频/压电打鼾检测门限，也不证明 summary 与片段必定相等。[H10,H38,H39,H62,H63；SnoringViewModel.smali:277–476]

7. 缓解结果能恢复到什么程度

DailyTrendsResponse 提供下列可空 Integer，并在 toDomain→RawDailyTrends→DailyTrends 保留：
  mitigationEvents、stoppedSnoringEvents、reducedSnoringEvents、ineffectiveExtendedEvents、cancelledEvents、elevationDuration、theoreticalSnorePercent、snoringReductionPercent、elevationAutopilotAdjustmentCount。
字段被缓存不等于手机实现它们的统计公式；本轮没有把 theoreticalSnorePercent 或 snoringReductionPercent 还原成一个本地计算公式。elevationDuration 在这条转换中是原样 Integer，也未据名称自行指定单位。[H19–H21,H60]

SessionResponse.mitigationEvents 是 List<Object>，在已追转换中保留至 Session.l。本轮对当前索引所有 Smali 的直接 iget-object 引用搜索只有 Session 的 equals/hashCode/toString 和 SessionJsonAdapter 写出；未恢复一个具有已知字段的 typed mitigation-event 消费器。这是精确字段引用范围内的未闭合项，不是证明整个产品不使用缓解事件。[H29,H50]

DailyTrends.m（mitigationEvents 数量）有明确非序列化消费者：P2.k.B 构造 loading_intelligent_snoring_mitigation 的参数文案，只有计数>0 时加入。邻近分支把 SQS snoringDurationSeconds 转整数分钟、把 snorePercent 用于 analyzing/processing 文案；这里的 processing 字眼不能当成检测算法正在手机运行的证据。[H31,H61；S1/P2/k.smali:615–697]

8. 可复用结论和未闭合边界

已回答：health/snore 响应字段与数组格式；trends 缓存/转换的生产路径；干扰日图小时分组、整小时桶数、缺小时默认值、期间缺值规则；两套 rating/阈值显示规则；打鼾时间拼接/期间减法/summary 来源；daysUntilAvailable 的 Pending 消费者；缓解计数的存储与一处文案消费者。

未回答：从原始传感数据到这些结果的检测算法、窗口/特征、模型权重、心搏与呼吸干扰的服务端定义/筛选、打鼾强度判定、缓解有效性计算、Pod6 各传感通道质量权重以及后台推理的版本绑定。本 APK 的正向已恢复链明确从远端结果开始，不能以此断言“整个 App 没有任何算法”或“所有平台/机型都只在云端处理”。

本报告属于静态源码/Smali 观察。时间桶算例只是由已读条件推导的例子；没有合成响应冒充实包，没有把资源说明当医学结论。
