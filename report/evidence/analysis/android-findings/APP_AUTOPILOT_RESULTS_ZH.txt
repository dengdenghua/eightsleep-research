Eight Sleep 中国版 Android：Autopilot 结果、解释与图表消费者
日期：2026-11-07；仅官方 APK 静态证据；不运行 App、不请求业务 API。

结论
本轮闭合的是“云接口结果→缓存→领域对象→回顾页面”的读取链，而非温控策略的生成链。
回顾接口的 DTO 已有调节时间、前后档位、type、phase、stage、reason，以及可选的
autopilot.description/template/type/data。App 对这些结果做分组、显示单位转换、图表
计数、标签选择，并把另一路 DailyTrends 的睡眠阶段叠到同一页面。
这里“Sleep response/睡眠响应”的分类是一个简单枚举分支：AUTOPILOT 且不是环境温度
类型就归为 SLEEP_RESPONSE。它不是本地睡眠分类或“看到某阶段就计算下一目标”的证据。
更具体地说，当前图表转换还丢弃 reason、metadata、description、template 和 data.delta；
不能因为接口中存在解释文字，就断言这些文字在本版回顾图表实际展示。

这里有实际本地算法，但属于缓存：J/P2/K.java:62–78 计算
  d = LocalDate.now().epochDay - entity.date.epochDay + 1

AR-R3：调节记录、解释字段和真实单位边界
AutopilotRecapResponse 包含 timestamp、temperatureAdjustmentCount、
pillowTemperatureAdjustmentCount、elevationAdjustmentCount、deltas、temperatureAdjustments、
pillowTemperatureAdjustments、elevationAdjustments、可选 temperatureSettingsUpdate。
J/.../TemperatureAdjustmentResponse.java:17–30,183–192 定义并转存：
  fromLevel/toLevel：nullable Integer；timestamp：Instant；reason：nullable String；
  metadata：nullable 六项 previous/current BedTime/InitialSleep/FinalSleep int；
  autopilot：nullable {description:String, template:String, type, data:{delta:List<Object>}}；
  type、phase、stage：非空枚举。
data.delta 的 toEntity 在 AutopilotTempDataResponse.java:46–51 强制取 [0] String、[1] Double。
这只是解释载荷的二元组映射；不能据 List<Object> 或 delta 名称认定为特征向量、模型参数。
metadata 见 TempAdjustmentMetadataResponse.java:14–20,120–121。

Smali 保留的 Moshi wire 枚举：
  AdjustmentType：autopilot/manual/smart（S2/.../AdjustmentType.smali:44–60）；
  stage：awake/deep/light/out/rem（AutopilotAdjustmentStage.smali:50–78）；

  autopilot.type：明确标注 autopilot-ambient-temp，另有 UNKNOWN 枚举
  （AutopilotTempAdjustmentType.smali:43–49）。没有把 UNKNOWN 当已证实的 wire 字符串。
stage 与 phase 是两种字段，不能把 BEDTIME/EARLY/LATE 叫 PSG 睡眠分期。

J/S9/g.java:59–73 保留字段到 N9.r；N9/r.java:49–63 与 O9/j.java:35–59 将温度 int 包装

所核实的标尺（LEVEL raw/10，摄氏/华氏为分段标尺），不意味着 JSON 中 int 本身是摄氏度。

AR-R4：文字解释实际保留到哪里；图表分类具体如何产生
description/template/type/data 先从 AutopilotTempAdjustmentResponse.toEntity 进入 S9.j，再
进入 N9.i；reason/metadata 进入 N9.x。故不能称这些字段从未解析。
但 J/P2/q.java:30–48 和 S/P2/q.smali:106–216 的图表 E(List) 实际执行：
  1. 排除 toLevel==null；排除 type==MANUAL。
  2. 构造 Le.i(timestamp,phase,stage,toLevel,fromLevel,type,autopilot?.type)。
     reason、metadata、description、template、data.delta 不传给 Le.i。
Smali incoming trace 证明该 builder 被 Recap collector 在行 207、221 分别用于 POD/PILLOW。

搜索完整 Smali 索引（查询 has_more=false）：
  LN9/i;->a/b/d（description/template/data）15 条，仅在 N9/i 自身 generated methods；
  LN9/x;->c/d（reason/metadata）10 条，同样只在 N9/x 自身 generated methods。
Java 同名字段检索也未见外部直接使用。这个范围的结论是“当前恢复的直接字段消费及
已闭合图表路径不显示这些字段”，不是对反射、动态载入或服务端 UI 内容的全局排除。

AdjustmentClassificationKt.getClassification 的 Smali:35–83 明确为：
  type==AUTOPILOT && autopilot.type==AMBIENT_TEMP → AMBIENT_RESPONSE
  其余 type==AUTOPILOT → SLEEP_RESPONSE（包括缺少/未知 autopilot.type）
  type==SMART → PHASE_CHANGE
  其余 → MANUAL
因此 SLEEP_RESPONSE 标签本身不证明识别到了某个睡眠阶段，也不证明手机执行了调温模型。
Le/i.java:158–209 再根据上述类别及记录自带 stage/phase 选择本地字符串资源：
  SLEEP_RESPONSE 且 stage 为 DEEP/REM/LIGHT：取该阶段 label 组合“detected”文字；
  PHASE_CHANGE：对 BEDTIME/EARLY/LATE/HOT_FLASH 选择 started/resumed 类文字；
  AMBIENT_RESPONSE：比较 from/to 的显示值选择 increase/decrease；from 缺失默认 increase。
这是真实 App 文字生成逻辑，不是把服务器 description/template 填进页面。

AR-R5：睡眠阶段关联、统计与“改善”卡片
S2/.../AutopilotViewModel$observeAutopilotRecap$1.smali:228–350 依次得到

累计数和当前页分类计数不能混为一谈：回顾 response 直接给三种 adjustmentCount。
当前 collector 对页面一个总计数采用 temperatureAdjustmentCount + elevationAdjustmentCount

DeltaResponse.java:12–18,92–94 已有 metric、previousValue、currentValue、deltaValue 整数，
S9.h.d 将它们直接转 N9.l；collector Smali:545–616 将它们复制给 Le.l 卡片。
AutopilotRecapMetric.java:22–42 的 metric 为 deep_percent、rem_percent、snore_percent；

因果归因和服务器如何产生这些数值，仍未知。

adjustment 时间落入区间选择强度（无匹配为 NONE）并构造 Le.g。这是回顾关联展示；
具体 snore/health 原始结果来源由本轮另一份 health 报告追踪，本报告不重复动作配置。

AR-R6：证据边界及尚未闭合入口
1. 本轮已覆盖实际 GET/调用者、三类 cache、DTO→entity→domain、回顾页面 combine、
   chart builder、分类、主要文字/数值映射、历史数字显示、阶段高亮实际 Smali。
   它们正面支持“此读取路径消费已标注结果”。不能由此宣称整个 APK、固件或云端
   都没有算法，也不能证明每个响应字段在国行 Pod6 当前账号都会填充。
2. 未获取任何业务响应，reason/template 的实际文案、服务器真实选取的 phase/stage、
   policy 输入/权重/预测时间窗、模型架构及输出到设备的对应关系均未由此恢复。
3. temperatureSettingsUpdate 的 from/to 对象在 recap/entity/domain 中保留；本轮未把它
   进一步闭合成独立“接受/拒绝建议”写回动作。图表 builder 丢弃记录 metadata 不能
   代替对其他建议卡片或偏好反馈入口的审计。
4. 独立 data_user/data/model/level_suggestions 家族（Profile/Cohort/CohortV2/FirstNight/
   Bedtime/TapToControl）及 presentation_home/.../FirstNightLevelSuggestionsSource 是
   已存在的后续候选；这轮没有据名称宣称其算法或反馈路径已恢复。
5. TemperatureAggregate、连续温度历史、独立 temperature-events 接口未在本轮新增追踪。
   本轮“温度历史”指 Autopilot recap 的离散 adjustment records。
6. 偏好/日程/闹钟/BLE 请求发送链见 APP_THERMAL_CONTROL_ZH.txt；实时 WebSocket 状态
   失效/刷新由父任务单独报告。不能把本回顾读链推断为设备实时控制优先级。
7. 对 Java 负面搜索不作全局结论；关键字段负面证据限定为完整当前 Smali 索引的直接
   字段引用，动态/反射依然是边界。所有结论均为静态观察或据此作的有界推论。
