旧 sensor MCU：采样、数值处理与正常输出链
2026-11-08；仅分析同一官方国行 MTK 固件包保留的 firmware-sensor.bbin，未运行固件、未连接或改动设备。

一、对象和证据边界
原件：mediatek/rootfs-selected/opt/eight/lib/subsystem_updates/firmware-sensor.bbin
大小 42,292 字节；SHA-256 a377d1be27d868c65fa4c90a34f70e9d3d45580236f67905ec56fe84cc595ba2。
初始化日志参数明确是 v3.3.1。文件名中的 sensor 不能证明用户实机正在使用这一版本；hwrev 数值也不是 Pod 世代编号。
本次闭合正常采样的入口→转换→缓冲→封包→UART/DMA 输出，并补清同主循环的 FDC 六路读数、故障状态、NTC/环境温湿度和温度合成。没有把全部 3.3.1 的每个命令、闹钟/马达/复位故障分支都称为已审。
final-functions 是最终伪代码+逐指令原字节证据；更早的 functions/repaired-functions/volatile-functions/typed-functions/evidence-functions 是保留的中间分析，引用以 final-functions 为准。分析者添加的名字以 analyst_ 开头，不是厂商符号。

二、装载和反编译修复
文件 offset 0 映射 0x08005000，BBIN 向量在 offset 0x80：SP=0x20002000，Reset=0x0800e085（Thumb）。这不只依赖向量猜测：Reset 0x0800e084 的真实指令从 0x0800f49c 复制 0x98 字节到 0x20000100，再清零 0x20000198..0x2000189b；0x0800f49c 对应文件尾部有效初始化数据，程序还引用 0x08005080 作向量表来源。
Reset→0x0800b1f0→初始化库→0x0800bedc 主循环。主循环内部有长距离 BL 回跳、无独立 prologue 的片段，被初次分析分成伪函数；RepairLegacySensor.java 将这些内部流标成 branch，合并 0x0800bedc..0x0800e083 已有指令，未改任何输入字节。
SRAM 标记可写，MMIO 标记 volatile，防止把硬件等待折叠为恒定死循环。软件浮点函数采用 __stdcall_softfp，参数在 r0..r3；曾生成的默认浮点寄存器结果不作结论证据。float/double helper 名称是基于其位操作、比较返回和调用现场恢复的语义，未声称与新 G0 helper 字节相同。
所有最终汇编中的 BYTES 对原文件地址减 0x08005000 逐条回读，结果见 BYTE_VERIFICATION.json；这是字节一致性校验，不是物理运行验证。

三、两条压电相关采样链，不能把旧文件只理解为一种格式
共同初始化位于 main 0x0800bedc；采样结构基址 0x20000334，底层环形缓冲 0x200008a4。主循环按 hwrev<0x700 与 >=0x700 选择不同实现。

A. hwrev<0x700：MCU ADC 缓冲→参考值校正→16 位双通道→0x32
main 设置 ADC 数据寄存器 0x40012440 到 RAM 0x200001d8 的 DMA。定时采样入口 0x08009b64 由 0x0800a49c 写入定时器回调表 0x200014b4，再由向量处理器→0x08008af4 调用；此处不是每次读取时发起一次 ADC 转换。
0x08008f48 按 hwrev 选择两个 ADC 缓冲索引：<0x100 为 [5,4]，0x100..0x2ff 为 [3,1]，0x300..0x4ff 为 [2,1]，0x500..0x6ff 为 [4,1]。这是逻辑采样通道映射，未据此推断物理哪条压电线。
计算顺序保持原代码的截断：k=uint16(floor(uint16[0x1ffff7ba]*3300 / uint16[0x200001fa]))；v=float32(raw*k)/4095000；若 double(v)>3.3，置为 float32(3.3)；q=uint16(uint32(double(v)/3.3*4095))。因此输出不是未经变换的原 ADC 码，包含参考校正、浮点舍入、上限处理和整数化。没有在该函数中看到时域带通、心率分离或分期推理。
0x08009b64 顺次读取两路，记录 {timestamp_ms:u32, sample0:u16, sample1:u16, setting0:u16, setting1:u16} 共 12 字节。时间在读两路前取得；没有同步快照锁或“本次 ADC 已更新”的判断，不能保证两路对应完全同一转换时刻。
默认 rate=100、环容量256条、每100 ms尝试发送；采样开始配置使用48 MHz参数和所请求rate计算定时器分频，见0x0800a49c。默认参数不是实测采样率。
0x080099c4 等待队列至少31条才开始一包；包前缀 32 02，随后为大端rate:u32、首记录timestamp:u32、两项setting:u16，再放双通道u16。后续记录仅在两个setting与首记录一致时合并，每包最多60条（14+4*n，最多254字节）。不同setting的下一条留给下一包；未要求逐条时间间隔相等，也不把每条时间都上传。

B. hwrev>=0x700：MCP3564 SPI 中断→四通道拼组→32 位双通道→0x34/0x41
main 安装 0x0800a2b8 到回调指针0x2000019c，向量0x0800b30c调用它；初始化文本和寄存器配置链标识 MCP3564。默认rate=500、环容量128条、每条24字节，每80 ms尝试发送。
0x0800a2b8 经0x41 SPI事务读取状态+数据；状态mask条件、数据有效位和通道标签通过后，把数据位24符号扩展为int32（保留25位有符号值），通道号仅接受0..3。首次接受的通道写入持久数组，重复通道只增加计数，不覆写该组的第一值。
以mask累计四路。mask==0x0f可立即入队；否则当距组起点达到3 ms，也会入队部分组。入队后只清mask和组时间，没有清四个数值槽；缺路可能沿用上一组的旧槽值，并不是自动补零。另有重复、缺路、超时及满队列计数。
full组耗时dt<2时，代码将记录时间改为 original_start+2-dt；否则保留原组起点。这里保留原式，不能等同“所有记录严格每2ms实际采样”。timestamp和setting记录于24字节记录尾部。
0x08009868 等待至少8条；包前缀 34 41，rate:u32、首记录timestamp:u32、setting:u32之后，实际只发送该记录四路数组的索引2、3两个int32，大端输出。每包最多15条（14+8*n，最多134字节），只合并setting相同的记录；索引0、1未写入这个正常数据包。
上述“缺路保留旧槽”直接来自旧镜像自己的producer，不是将新G0分析套过来。其实际发生频率需要设备原始记录。

C. 共同缓冲与链路
0x08009b30 环写：write_count-read_count==capacity 时拒绝新记录，成功才复制和增write_count；不是覆盖最旧数据。两个packer每次工作最多约500 ms，未消费的记录留待下次。
rate在packer里读取全局当前值；每条记录不携带自己的rate。这里不能把header rate当作每条记录均已按该频率采集的证明。
0x08008330 发帧：0x7e开头、1字节payload长度、payload、CRC16高字节在前；CRC初值0x1d0f、多项式0x1021。0x08008124 对0x7e/0x7d作0x7d+异或0x20转义。
0x080080e8 的实际调用现场给r0=发送缓冲、r1=累计长度，经0x20000700→0x0800af2c；后者复制到发送缓冲并配置UART寄存器0x40013828及DMA。伪代码中间版本曾把间接调用的长度参数漏掉，汇编已确认。这里的发送调用完成不等于云端接收确认。
本次审计的正常生产链出现0x32、0x34/0x41、0x33及0x31状态包；未把未见的0x30生产路径虚构出来。

四、FDC 六路：本地转换和状态诊断，非睡眠分类
main在hwrev>0x2ff分支初始化两侧FDC1004上下文；0x0800a64c设置3个轮询通道、各通道CAPDAC初始0。配置的CAPDAC编码为uint32(offset/3.125)&31，寄存器读回再乘3.125检查；不能据此声称本版本有自动寻找最佳CAPDAC的算法。
50 ms调度交替选两侧上下文，每侧又分“发起下一通道”与“检查/读取当前通道”两步；读成功才将state置为下一步。三通道顺序轮转，实际刷新周期受主循环、就绪位及事务成败影响，不能把50 ms当作六路每路同频同步采样。
原始两个16位寄存器拼接后用ASRS #8得到有符号24位值，再乘2^-19得pF；汇编0x0800dd88..0x0800dd9c明确是算术右移。负数在处理槽写成-1.0，但原始浮点结果另外保留；读取失败同样写-1.0。未就绪则不覆盖，旧值继续留在槽中。
0x080081dc取出六路当前处理槽和当前系统时间。0x33每500 ms封包：1字节type、4字节时间、左右状态各u16、六个{id:u8,value:i16}，共27字节。value为float32(pF*100)向零转int32再截为int16，高字节在前；-1.0因此编码为-100。输出逻辑顺序是左[2,1,0]、右[0,1,2]。时间是取快照/发包时刻，不是六个独立采样时间。
status更新在另一个30秒定时分支，故0x33的值和状态不保证同龄。0x08009398检查任一路相邻快照差<1e-9，且该值不在[15.9999,16]，用于累计停滞计数；0x080092f0在三路两两差均<=0.03时累计另一个计数，否则归零。0x080094b0检测任一路严格0<值<0.5，并在main累计异常次数。
0x08009528：三路全在[15.9999,16]→1；停滞计数>=7→2；否则近似一致计数>=7→3；否则0。它不是根据人体运动判“在床/离床”的实现。main还按状态或低值次数保留上次健康时间、超过约60秒进入传感器/总线复位路径；本次仅核正常状态到该边界，没有运行复位。

五、温度与环境数值处理
0x0800b400按硬件配置选择热敏电阻表，ADC映射值0x18视为缺失并返回-100。模式0拒绝ADC<50；模式1拒绝ADC<50或>4050。
模式0：R=R2*(4095/ADC-1)；模式1：R=R1/(4095/ADC-1)。随后T=float32(1/(ln(R/10000)/beta+1/298.15))−273.15，再转float32；中间R运算为float32，ln/倒数用double。
表：rev0..2使用mode0/beta3435/R2=10000；rev3使用mode0/beta3936/R2=10000；rev4..0x1ff与0x200..0x2ff使用mode1/beta3380/R1=10000；rev0x300..0x4ff、0x500..0x71f、>=0x720使用mode1/beta3380/R1=7150。每表完整11项ADC索引见 TABLES.json。
0x0800b354实现ln的级数：z=(x−1)/(x+1)，累计2*(z+z^3/3+z^5/5+...)，相邻double累计值相等才退出，没有固定迭代上限。这里恢复的是代码的停止条件，未宣称所有异常输入都能终止。
温度合成函数0x08008da0明确是(max(a,b)+0.2*min(a,b)+0.1*c)/1.3；0x08008ef4和0x08008e2c在调用前处理-100缺失和二/三点分支。三点正常全有效时先对外侧两点合成，再用中间点与该结果的max作参考，第二次合成。它是本地温度估计，不是心肺/睡眠信号融合。
0x0800b710按rev路由：最旧版本两侧分别读逻辑3/6；中间版本使用2/4和7/5；较新版本使用2/3/4和7/6/5，逻辑8作参考。0x0800b7c8在rev>=0x720且非8..10通道时，只有FDC相关flag清零且距标记>9 ms才刷新，否则返回温度缓存。
0x08008c5c还用芯片校准区和ADC参考计算内部温度，公式为((raw_temp*cal_ref/raw_ref−cal_temp30)*80/(cal_temp110−cal_temp30))+30。函数维护一个约1°C门槛缓存，但返回寄存器r0加载的是本次计算值（0x08008ce0），不能把它误写成返回滤波缓存。
环境I2C周期5秒：raw温度=(hi<<8)|(lo&0xfc)，T=raw*175.72/65536−46.85，仅0<T<70时更新；RH=raw*125/65536−6，仅RH>=0时更新，未见上限100夹断。失败/不合格值保留缓存，事务与CRC最多重试3次。CRC8例程0x080081b0使用多项式0x31；环境读数在0x0800b840的逻辑8/10查询路径使用。
温度查询命令0x2a/0x2f通过0x0800b840选值，乘100向零转整数，输出逻辑编号+大端i16；缺失有单独sentinel，湿度逻辑10与其他通道不同，不能统一当作-100*100。

六、温度反馈与状态输出的已核边界
0x0800b560由定时回调每100 ms评估或参数更新后立即评估；侧温度−100→状态0；侧温度>目标+0.5，或相关最高温>40.5，或内部温度>66→状态2；侧温度<=目标−0.5且相关最高温<=39.5且内部温度<=64→状态1；中间带保持之前状态。
0x080090ac将其写入侧状态字节，并保留额外覆盖条件；后续主循环汇总左右状态、检查电流和输出电源状态，0x31携带时间、左右状态、电流及选侧字段。这里只把温度算法到本地状态/正常报告链闭合，没有把泵/加热器完整电气故障保护另称已全部复现。

七、能下的结论与下一步
已能确定：旧sensor在上传前就会做ADC参考校正和量化、MCP符号扩展与分组/缺路旧值保留、FDC单位换算和负值sentinel、低频状态诊断、温湿度转换与温度合成。不能再把所有“原始数据处理”都归为云端。
这份静态材料没有补出生产睡眠分期、HR/HRV提取、压电人体源分离模型或云端温控策略；温度加权及FDC故障分类不能冒充那些算法。
现在仍需外部事实的项目：实机实际选用哪份sensor固件与hwrev、通道与物理传感器位置对应、真实缺路/重复/时钟行为频率、传输丢包和云端接收结果。只凭本件不能判定Pod5/Pod6当前启用旧实现。
本轮保留的静态未覆盖范围：闹钟/马达全部时序、所有命令错误和硬件复位恢复、I2C/SPI底层每种超时、电气故障保护全组合。它们不是本报告采样数值主链的缺环；若后续审计扩大到旧附件控制全量，应单列，不以“运行时待办”掩盖仍可读代码。
NUMERIC_EXAMPLES.json为依据代码写的有限输入例子，不是固件执行、不是实机测量。SOURCE_LEDGER.json和COVERAGE.json记录实际读到的入口与范围。
