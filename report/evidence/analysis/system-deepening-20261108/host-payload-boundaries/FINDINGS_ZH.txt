Frank USB：0x3c / 0x33 在 LSP 验收后的 payload 边界
2026-11-08；限定已有原始 ELF，静态指令 + 有限合成模型。

概要

本轮没有重复把正常字段布局当新发现，而是核对异常长度如何走到状态写入：
1) 0x3c 按总长度向下取整计算 ADC 块数，不要求固定 376 字节，也不检查 64 字节余数。一个本来 376 字节的 payload 若变成 375 且仍通过 LSP，主控会解成 4 条 ADC，并把原第 5 条 ADC 的一部分当作 IMU，而不是报短包。
2) 0x33 的原指令确为“长度 >27 退出；否则解码”。解码固定读取到 payload[25]，所以 0..25 字节的短 payload 会用到当前有效载荷之外的接收缓冲字节；26/27 可覆盖所有读取，28 反而不解码。
3) USB caller 先清零的是独立的 20 字节输出对象，不是 LSP 输入缓冲。0x33 decoder 退出后没有成功标志检查，继续请求 CapSense 处理。短 payload 的旧值来源可能是同一 LSP 缓冲残留，不能误称上一条“解析结果缓存”直接被复用。

这些是本包条件性代码行为。未运行 Frank/固件、未访问设备/账号、没有实机失败频率或云端后果，也未确认当前 K60 普通生产流会发送 0x33。

1. 进入这些分支的准确前提

沿上一轮已闭合的真实 UsbSensor 对象/端口路由，本轮重新保留关键入口指令：
  LSP CRC true → 00219b34 → 00236174 → UsbSensor 0027e7b0
00219b34 从 LSP body 首字节取 opcode=byte&0x7f、flag=byte>>7；传下去的指针为 body+1，长度为 body_length-1。下文所有长度均不含 opcode。
00236174 只在所审 flag=0 且对象状态=2 的分支，通过 vtable+0x68 进入 USB 固件事件处理。0xb3/0xbc 虽低7位为0x33/0x3c，高位1会走其他通用处理，不能直接套用这些事件分支。上层更新仍有可用标志、计时与协程调度门控。
证据：pass2/00219b34.txt、00236174.txt；上一轮 host-usb-receiver/RAW_TABLES.json 和 FINDINGS_ZH.txt。

2. 0x3c：长度先决定布局，余数未拒绝

0027e7b0 的该分支：
  payload_len <120：退出，不进入本分支的逐行 mapper/传感计数更新。
  否则读取 BE32 tick、BE16 flags、BE16 frequency，共8字节。
  N = floor((payload_len-8-48)/64)
  ADC 区 = [8, 8+64*N)，IMU 区 = [8+64*N, 8+64*N+48)
  后面余下 0..63 字节不再读取，也未要求必须为0。
BE32/BE16 helper 0045f6e0 / 0045f6b4 固定读取4/2字节并返回4/2；本轮按原始指令核过，不把伪代码里的变量返回值当可变长度编码。

正常5条ADC的payload为376。有限例：
  376：N=5，IMU起点328，无尾余数。
  375：N=4，IMU起点264，忽略末63字节。原第5条ADC起点也为264，因此IMU字段来源改变。
  377..439：仍N=5，原IMU仍位于328，末1..63字节被忽略。
  440：N=6，IMU起点392；第6条ADC把原IMU48字节与追加区前16字节拼作64字节，剩下追加区48字节作IMU。
以上序列通过入口需要对应长度与CRC自洽。不能由这个合成例推断现场少一个USB字节仍一定能通过旧CRC。

在 LSP body 不超过2048、payload为120..2047、输入期间不变的范围里，N的上述算法使每条64字节ADC和48字节IMU读取都落在当前payload内；本轮对这1928个长度做了有限算术检查。这不证明内容符合物理采样布局，也不覆盖上一轮超2048的CRC读范围或并发改写。

原指令入口：pass1/0027e7b0.txt 中 0027f314..0027f3fc（头与长度）、0027f520..0027f5ec（IMU）、0027ee38..0027eeac/0027f108..0027f1fc（ADC与更新）；具体完整范围以导出文本为准。

3. 0x3c：哪些状态被清、哪些仍推进

frequency=0：头字段已经写入本次协程局部对象并标记存在，随后记“zero frequency”日志并退出；未进入本分支逐行计数/mapper。没有证明其他全局日志计数完全不变。
frequency>0：样本间增量为整数 1000/frequency，未见要求其等于已配置500，也未见本分支上限检查。合成frequency=1001时增量为0，多条ADC给mapper的tick参数相同；这些调用和owner+0x3c80计数仍逐行推进。是否触发后续补点/诊断由mapper状态决定。

每包 IMU 先复制原始模板 0046bdb0 的24个0x7fff，再仅写 flags bit12..15 启用组。每条 ADC 先复制 00472f20 的0x7c字节模板，16个ADC槽初值均0x7fffffff，再仅写bit8/bit9启用组；禁用字段不是上一条值。本轮保留模板原字节于 RAW_TABLES.json。
没有对其他flags位做全面合法性拒绝；是否开启的组只由这些位决定。即使所有这些组禁用，仍能形成全sentinel行并走 mapper /计数。

每个已解出的ADC行：传入 0021a5c0 的check/update参数为1，tick参数=header_tick+行增量（32位加法）；随后本地偏移+=整数步长，owner+0x3c80 +=1。mapper可以更新共享时间上下文；return非0的分支额外请求一次001e20d0，普通分支还会请求一次。因此计数增加的是解码行，不等同最终回调/上传行数。模型仅记录mapper参数、解码行和计数差，不假装模拟全部时钟漂移、协程异常或日志队列。

4. 0x33：长度判断、读端点和独立输出对象

0021abe0：
  0021ac0c cmp x1,#0x1b
  0021ac10 b.hi 0021ad40
因此无符号 payload_len>=28 时直接回到函数尾；不存在“>=28才安全解码”的反向解释。
小于28时，固定读取：
  BE32：偏移0..3（tick）
  BE16：4..5、6..7、9..10、12..13、15..16、18..19、21..22、24..25
中间跳过8、11、14、17、20、23。本轮不猜这些被跳过字节的物理含义。最高读取端点为25，需要26字节覆盖；27字节末字节未被本decoder读取；28字节直接不解码。

USB caller 0027efa4 将协程+0x5c写4字节0；0027efac将+0x60和+0x68各写8字节0，共20字节，即32位时间字段+8个16位字段。0027efc0调用decoder后直接到0027efd8请求001e0ec0；没有检查decoder返回值，decoder本身也没有已证成功布尔契约。
这意味着：
  len26/27：填充20字节输出并继续处理。
  len>=28：decoder不写，继续处理caller预先清成0的20字节对象；不是“保留上一条输出”。
  len0..25：仍按上述固定偏移读。若接收缓冲已有上一帧内容，会把没有被当前短body覆盖的字节读进本次结果。

共享LSP接收器001d9bc0在起帧时清长度/计数/临时CRC，没有memset整个2048字节body；只在实际body token到来时覆盖对应位置。CRC仅验当前声明body，因此不能保护0x33 decoder后来读取的声明范围外残留。
本轮以明确非零预置+上一份有效26字节payload作来源，再收到有效CRC的0/4/25字节新payload，记录每个跨末尾字节确实来自前帧。没有假定真实初始RAM为0，也没有读取本机或目标真实RAM。所有这些偏移仍落在同一2048字节接收区内，不称整个分配越界或内存崩溃。

0x33 调用0021a5c0时w4=0，直接读取现有时间锚点返回时间/差值，不进入该helper更新last_tick/counter的分支；随后按uint32差值/1000加到输出时间。异常短输入里的tick也可能来自残留，但本分支不因此推进共享时间锚点。也未见它增加0x3c专用owner+0x3c80计数。

5. 0x33 结果是 CapSense 路径，不是全部睡眠 raw

001e0ec0创建001e61d0协程，再创建001ed1d4；其日志名为enqueueCapSenseSide。001ed1d4首先检查raw logger+0x14e0是否存在；没有启用对应模式时记录“called before enableA30Mode”并返回。有该对象且符合已审队列条件时，20字节结果原样复制入该侧deque；拥塞分支还涉及等待/flush，本轮没有把“请求callback”写成“必定已入队或云端收到”。
UsbSensor 0027a980 在revision>=0xA00分支调用001e2bb0→001f6920(enableA30Mode)。001f6920在+0x14e0缺失时建立CapSense缓冲；该分配不以all-types开关真假为条件。可以说明本包存在启用条件，不能据此断言当前设备状态。
现有sensor-frame-bounds的普通采样生产链明确为0x3c；本轮只限Frank，没有新增MCU 0x33生产者分析，也没有实机包。因此0x33是已绑定的条件事件入口，但是否为当前K60正常输出、何时触发、频率多少仍未知。不泛称所有睡眠采样均受此问题影响。
