1. alarm 消费者的名字会误导人
AlarmRepository 构造函数启动 j9.a，其 access$observeTempDialEvents 实际 const-class Ia.a（Alarm），从 Da.v.d SharedFlow 过滤，再将事件送给 j9.r；不是温度事件处理。[E01,E02,E04]
这条流接在已证实的 WS JSON→domain→同类时间排序/150ms 合并之后。SNOOZE 与 DISMISS 都属于 Ia.a 这个类，所以密集到达仍受同类合并约束，不能默认每条原始通知都触发一次处理。

2. SNOOZE 与 DISMISS 先改本地缓存，再取云端最新闹钟
j9.q 的枚举表将 SNOOZE=1、DISMISS=2。[E03]
j9.r 按 event.alarmId 调 n9.b.h，实际 SELECT * FROM alarm WHERE id=?。如果有旧记录：[E04,E05]
- SNOOZE 传 copy mask 0x1fefff：只将 isSnoozing 置 true，保留原 snoozedUntil、nextTimestamp、endTimestamp 等字段。
- DISMISS 传 copy mask 0x1f5fff：将 nextTimestamp 与 endTimestamp 置 null；其余此 helper 可复制字段保持。没有在这里自行生成 dismissedUntil 时间，也没有按 event.time 重新排闹钟。
修改后调用 n9.b.j(event.userId,entity)，复制 userId 与当前 System.currentTimeMillis 更新字段，提交 Room 写事务。[E09,E24]
无缓存则跳过局部修改；两条动作分支都继续 fetchAlarms(event.userId)，并由 P2.q.r 真正收集该 flow，不是只创建一个无人消费的请求对象。[E04,E06]
fetchAlarms → j9.j → i9.a.b 是 GET v2/users/{USER_ID}/alarms；响应 alarms + recommendedAlarm 交给 j9.k → n9.b.k 写入缓存。[E07,E08,E23]
所以事件主要用于快速同步状态并回源读取；当前通知处理不是控制设备的 snooze/dismiss API 调用，也不是本地推断闹钟何时应当触发。

3. 缓存确实进入 UI，不停在 repository
AlarmRepository.observeAlarmsForUser → n9.b.d 订阅 Room 的 SELECT * FROM alarm WHERE user_id=?；实体经 p9.a.c 转 domain，m9.F/m9.E 与显示设置组合，m9.D 将时间/档位转为界面模型。[E10–E13]
HomeScaffoldViewModel.observeAlarms 合并闹钟与 napStatus；成功 collector $observeAlarms$1$3$1 调 processAlarms。[E14,E22]
processAlarms 遍历 active 或 upcoming 记录；第一个 active 调 showActiveAlarm 更新界面状态；找不到 active 时清除 active alarm 的界面模型；随后按下一条相关时间或默认 5 分钟安排刷新。[E15,E18]
active 的实际判断是 enabled 且 nextTimestamp <= 当前毫秒 <= endTimestamp；缺任一时间则 false。upcoming 是 enabled 且 nextTimestamp 在当前至 24 小时窗口内。[E16,E17]
因此 DISMISS 的局部清 nextTimestamp/endTimestamp 足以让这条 UI active 判断变 false；真实设备是否停止和随后的云响应是否一致，需要运行时观测。SNOOZE 的本地 isSnoozing=true 不等于已经有新的 snoozedUntil 或完整重新排程。

4. base-preset：可解析，不等于有业务消费
PodEventResponse$BasePreset.toDomain 只构造 Ia.b(deviceId,userId,timestamp)，无角度、预设 id 或设置载荷。[E19]
已审阅完整直接数据通路：Da.r → Da.v.g 内部 channel → Da.u 排序/合并 → Da.t → Da.v.d SharedFlow。[E20,E27；既有 live-results]
本轮精确四 DEX 搜索及逐点分类：
- LIa/b; 25 个匹配，全部是 Ia.b 自身或 BasePreset.toDomain/桥接；没有外部 const-class/check-cast/字段消费者。
- Da.v.g 3 个匹配：构造写入、Da.r 发送、Da.u 读取；没有其他分流。
- Da.v.d 4 个匹配：构造写入、Da.t emit、AlarmRepository 类型过滤 Ia.a、TemperatureRepository 类型过滤 Ia.d。后两者均不接收 Ia.b。
- Ia.e 抽象父类 23 个匹配，限于 DTO 转换和上述事件分发；没有另一个通用业务消费者。
BaseRepository 构造依赖为 API、exception handler、preset cache、scope，未接收 PodEventsRepository；不能因为叫 base-preset 就补画“事件→BaseRepository刷新→UI”的不存在证据边。[SEARCH_LEDGER.json / E02,E21,E27]
结论限定：此 APK 已恢复的静态字节码通路中，该事件进入分发流后没有已绑定的业务消费。反射/动态代码/服务端联动仍超出这一直接关系结论。
