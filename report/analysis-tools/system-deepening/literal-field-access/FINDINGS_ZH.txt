============================================================
一、结论置顶
============================================================

把字段访问的识别从「pseudo-C 里的 param_2 + 0xNNN」扩展到「指令里的字面量
偏移 + [base,rX] 寻址」，得到一张大一个数量级的字段图，并借此把两个此前
无见证的空洞判定为有字段语义。四项闭合：

  1. 字面量偏移访问共 2609 处、224 个不同偏移、114 个函数。这比只看
     param_2 的 156 个偏移多了 68 个，而且能看到基址寄存器与读写方向：
     读 1291、写 464、其它 854。
  2. 对象绑定判据：同一函数内还访问了 ≥2 个已覆盖区间里的不同偏移，
     才认为它操作的是同一个布局的对象。114 个函数里 68 个满足。
     这个判据是本轮的核心——没有它，字面量偏移会把别的对象的字段
     混进来。
  3. 空洞 1c08..1c0c（4B）闭合：偏移 0x1c08 在 5 个已绑定函数里被访问
     7 次。空洞 0234..0258（36B）也闭合：偏移 0x24d/0x24e 在
     sensor-log-producers/pass1/callsites.asm.txt 里被访问，该函数已绑定。
     空洞见证从 10/14 升到 **12/14**，剩余 43B（027c..02a0 与 3e01..3e08）。
  4. trampoline 簇被解码为**分支链而非跳转表**：6 组「ldr 字面量 → bl stub」
     配对，其中 08016e02..08016e14 四组连续。字面量语义可读：
     0xbf800000 = float -1.0f，0xff7fffff = 清第 23 位的掩码，
     0x2000a498 是 RAM 地址，0x080252a8 是日志格式串
     「[sensor] unshielding took %ums before settling time start」。

硬数字：41 项字节核验 0 失败、28 条模型断言 0 失败、区间导出 496 条指令
逐字节比对、6 组配对的字面量值全部从冻结镜像独立读出复核。

============================================================
二、为什么原来的字段台账漏掉这么多
============================================================

主分派 0801d888 的字段写法是伪 C 里的 `param_2 + 0xNNN`，所以之前的提取
只在伪 C 文本里找这个模式。但同一份对象在别的函数里是这么访问的：

  ldr r3,[0x080161f4]   ; 字面量值 = 0x1c08（就是字段偏移）
  ldrb r3,[r7,r3]       ; r7 是对象基址

偏移在 literal pool 里，基址在另一个寄存器里，伪 C 里根本不出现 param_2。
上一轮也因此得到「0x1c08 无见证」这种假阴性。

本轮的提取规则：
  - 字面量值 < 0x3e88（对象尺寸下界）才可能是字段偏移
  - 其后 400 字符内必须出现 `[base,rX]`，且 rX 与装载寄存器同名
  - 按紧接着的那条指令判读/写：ldr = 读，str = 写

============================================================
三、绑定判据与被拒绝的假绑定
============================================================

只看偏移值是不够的。0x24d / 0x24e 这两个值在 4 个函数里出现：

  report-object-layout/pass1/08019bac.txt
  local-tmag-closure/pass4/08023958.txt
  local-sensor-recovery-followup/pass2/080224f0.txt
  post-layout-closure/pass6/08018744.txt

它们都不能算作主对象空洞 0234..0258 的见证。两条独立证据一致：

  1. 绑定判据：这 4 个函数除候选偏移外没有再碰任何已覆盖区间的偏移，
     即它们操作的是别的对象。
  2. 基址证据：08019bac 的 0x250 块在主对象里的基址是 **0x3b48**
     （上一轮构造函数台账已记录）。块内偏移 0x24c/0x24d/0x24e 对应主对象
     的 **0x3d94 / 0x3d95 / 0x3d96**，与 0x0234..0x0258 无关。

其中 0x3d94（ID 字节）落在已覆盖区间 [0x3b48, 0x3d98) 内，进一步说明
它不属于那个空洞。

真正让空洞 0234..0258 闭合的是另一处：sensor-log-producers/pass1/
callsites.asm.txt 里对 0x24d/0x24e 的访问，该函数本身已绑定。

所以「有候选」和「有见证」是两回事。HOLE_WITNESSES.json 里每个空洞都同时
记录 candidate_accesses 与 bound_accesses，并把被拒绝的绑定连同理由写进
rejected_binding 段。

============================================================
五、trampoline 簇是分支链
============================================================

区间 [08015e00, 08017000) 共 496 条指令。6 组「字面量装载 + 紧随调用」：

  位置        寄存器  字面量地址    值           调用目标
  08016142    r0      080161e8      0x080252a8   08012754（日志）
  08016e02    r1      08016f8c      0xbf800000   08015f08
  08016e08    r0      08016f90      0xff7fffff   08015f28
  08016e0e    r0      08016f90      0xff7fffff   08015f46
  08016e14    r1      08016f90      0xff7fffff   08015f64
  08016f18    r0      08016fc4      0x2000a498   080134be

值的可读语义：
  0xbf800000  按小端 IEEE754 读 = **-1.0f**，典型的无效值哨兵
  0xff7fffff  按位取反 = 0x00800000，即**清第 23 位**的掩码
  0x2000a498  RAM 地址
  0x080252a8  冻结镜像里的字符串「[sensor] unshielding took %ums before
              settling time start」

四组连续 case（08016e02/08/0e/14）把 -1.0f 与清位掩码交给 stub，形态上是
故障/状态清除路径；08016142 那组把格式串交给日志函数，说明同一区域还承担
诊断文本格式化（栈缓冲在 sp+0x20）。

派发门控在 08016e1a 的 `cmp r2,#0` / `beq 08016e22`，即 r2 为 0 时跳过
08016e1e 的调用、直接落到 08016e22。

**每个 case 属于哪个 switch 的哪个分支仍然没有解析**——需要把派发器的
跳转表与调用点绑定，本轮没有做。

============================================================
六、边界
============================================================

  1. 覆盖率不变：11297/15880 = 71.14%。本轮增加的是**字段证据**，
     不是块级覆盖，空洞字节仍不计入覆盖。
  2. 两个空洞（43B）仍无见证。
  3. 绑定判据是启发式：≥2 个已覆盖偏移只是「同一布局」的强提示，
     不是形式化证明。已把判据本身写进台账，可被反驳和替换。
  4. trampoline 簇的分支归属未解析。
  5. 169 个大函数内部地址仍无函数体，需要重新反汇编，越只读边界。

（build_round11.py）全部通过，两组独立计数在 2609 访问 / 224 偏移 /
68 绑定函数 / 2 闭合空洞 / 6 组配对上互相吻合。
