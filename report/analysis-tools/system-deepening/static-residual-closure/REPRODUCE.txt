  · 把 34 个导出文件里 3448 条已解码 INSN 的机器码逐条对回原件；
  · 把 1606 条 REF 注解里的 flash literal 按 u32 对回原件；

  · 57 条关键指令锚点（0x18c 三处构造、0x1a0/0x1a4 读写、

  · 14 个 flash literal 锚点；
  · 10 条原始 Thumb-1 半字：K87 / K90 setter 在工程里没有函数体，

residual_models.py 只读 RESIDUAL_TABLES.json 与 pass2 的 14 个 setter 导出：
  · 验证 5 张通道表都是 0..7 排列、只有 3 种、算出逆置换；
  · 从 setter 指令自动提取配置对象槽位台账（含 adds rN,#0xfc 的偏移累加），
    输出 CONFIG_SLOTS.json；
  · 重放 14 行累加分派，求 +0x1a4 的最终表指针、K90 对 +0x18c 的影响，
    并枚举 sku / devicesn 的条件分支；
  · 按两条 BRR 公式枚举 2 时钟 × 8 波特率 × 16 表索引 = 256 组，
    含范围检查、bit3 清零性质与反事实。

三个脚本都只把 BBIN 当数据读，不执行固件、不联网、不访问设备或账号。
跑完应分别看到 status PASS / 0 failures。

四、复跑时的已知坑

  · 0xc6 这个立即数有三种移位：`<<1 = 0x18c`、`<<2 = 0x318`、
    `<<5 = 0x18c0`。只有 `<<1` 是本轮讨论的 byte 状态位；
    不要把所有 `movs rN,#0xc6` 都算成同一个槽位。
  · setter 常在写入前 `adds rN,#0xfc`，槽位台账必须累加这个增量，
    否则 `[r4,#0x18]` 会被误记成 +0x18（实际 +0x114）。
  · K87 / K90 setter 在工程里没有已解码函数体，`TARGET ... function=none`
    是正常结果，用原始 Thumb 半字解码，不要改动工程去反汇编它们。
  · 字符串表 idx4/5 是 K10/K05，分派表阈值行 4/5 是 0x0A05/0x0A10
    （K05/K10），顺序互换，不能按位置硬配。
  · 8 个常见波特率在镜像里全都找不到 4B 常量；任何具体 BRR 数值都必须
    标明是参数化模型输出，不能写成「固件固定使用 115200」。
