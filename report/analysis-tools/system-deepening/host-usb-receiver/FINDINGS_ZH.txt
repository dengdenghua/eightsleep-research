MTK Frank：USB 传感字节进入 LSP 后怎样验收、丢弃和重新同步
2026-11-08；静态代码证据 + 有限合成检查；没有执行目标、连接设备或查询账号。

结论

这条接收器确实用于本包 UsbSensor 的运行固件路径，并非仅凭“同一个通用解析函数”套用。USB 接收先经过 LSP 帧边界、长度、转义和 CRC，之后才分派 opcode。它能拒绝本轮特定的“body 已改变、CRC 仍旧”序列，并从后续未转义的 7e 重新起帧；不能据此保证所有混合字节均被安全拒绝、下一帧一定恢复，或通过 CRC 就是新采样。

本轮最重要的新边界是：2048 字节限制只用于接收 body 的写入，没有作为声明长度的拒绝条件。超过该容量的 body 仍递增计数；若完整走到 CRC，CRC 用完整计数读取，而非截断到 2048。这里可证的是“读取超出配置 body 子缓冲范围”；并未证明超出整个 C++ 对象或堆分配，也未证明实机一定崩溃。

1. USB 路由与运行模式已经单独闭合

全局初始化 0017aeb4..0017af80 分别分配两个 0x3d30 对象，调用 0019e7f0，将结果写入 005e36a0 / 005e36a8。0019e7f0 写 vptr=005c79f8；原 ELF 的 RTTI 名称为 9UsbSensor。0018a874 / 0018a89c 将这两个对象传给 00233350；后者将对象保存在协程 +0x48 并设置执行入口 002349f0。

运行固件的 0027a980（stateBootloaderStartFirmware）和 CDC 重开分支 0027abc0 都调用：
  00280b10(owner+0x20f0, 1, owner+0x3c48中的端口编号)
中间的 1 启用两字节长度。对象 init / unknown / bootloader 路径还存在 flag=0 的一字节模式，不应笼统说整个 USB 生命周期永远为 BE16。

00280b10 绑定如下字段：
  LSP 接收区 = owner+0x3170；配置容量 = 0x800（2048）
  输出长度 = owner+0x3168；端口编号存在 wrapper+0x1070
  输入 callback = 00280ad0 → 002379a0
注意此处保存的是端口编号，不是直接保存 OS fd。002779a0 的 CDC 分支经 00237470 打开对象的 path，并把 fd 放入全局端口表 005e0a30（每项 8 字节）。002379a0 从同一表取 fd，调用 read(buffer, requested_length)；非负 read 结果直接返回，错误则返回 0，errno 0xb 之外还记日志。该输入链是本地 tty/USB 字节流，不是云端 HTTP API。

002349f0 先检查 vtable+0x48，再调用 00280ba0→001d9bc0(owner+0x20f0)。这个 gate 经 00276710→00258df0 读取端口管理对象的可用标志；没有把它称为“内核保证已有完整数据”。CRC 成功后仍需本次更新的计时/状态条件允许、长度非零，才由 00219b34 拆出低 7 位 opcode、高 1 位标志、body+1 指针和 length-1。

后续 vtable+0x60=002334f0 创建 00236174 协程；标志为 0 且对象状态为 2 时，再经 +0x68=00278c00→0027e7b0 进入 UsbSensor 消息处理。不同标志和状态有其他分支。CRC 成功不等于某个 ADC/IMU 事件已经被业务层接受，更不等于云端已接收。

证据：pass2/0027a980.txt、0027abc0.txt、002779a0.txt、00237470.txt、002379a0.txt；pass3/0018a510.txt；pass4/005e36a0.txt、005e36a8.txt、00278c00.txt；pass5/0017ae00_0017afb0.txt；pass6/0019e7f0.txt、002334f0.txt；pass7/00236174.txt、00258df0.txt；RAW_TABLES.json。

2. 帧格式：CRC 覆盖 body，不覆盖长度

运行模式的线上格式为：
  未转义的 7e | 转义后的 BE16 长度 | 转义后的 body | 转义后的 CRC 高字节、低字节
body 首字节包含 opcode/标志，属于 CRC 覆盖范围。001d9dc0 的初值为 0x1d0f，多项式 0x1021；每个 body 字节先异或到高 8 位，再移位 8 轮；未见末尾异或。长度字段、起始 7e 不参与该 CRC。发送器 001d9ac0→001da1f0/001d9f34 与此一致。

001d9bc0 收满声明长度后读取两个 CRC 字节；状态先回到 0，再对 body[0:received_count] 计算 CRC。匹配返回 true；不匹配继续在当前已读字节中扫描，可以在同一次调用中找到下一帧。该函数内未见专门的 CRC 失败计数/日志/错误码；只有成功与暂时没有更多输入的布尔区分。外围有“lsp receive timeout”日志，不能把每次 CRC 不匹配说成立即触发超时或重连。

原指令：pass1/001d9bc0.txt 001d9ce8..001d9d14；001d9dc0.txt 001d9dc0..001d9e14；发送器见 pass2/001d9ac0.txt、001d9f34.txt、001da1f0.txt。

3. 转义处理宽松，重新同步有前提

001d9e40 的规则是：
  普通 7d：设 escape_pending，继续取下一字节。
  escape_pending=1：无论下一字节为何，都 XOR 0x20，作为普通数据返回。
  其他情况下的 7e：作为分隔符返回。
因此并没有“只有 7d5d / 7d5e 才合法”的接收检查。合成例里的 7d20 会变成 00，若 CRC 一致，帧能通过。7d7e 则变成普通数据 5e，这个 7e 不再具有重同步作用。

escape_pending、长度解析状态、已收 body 计数在 read 返回 0 时保留。合法转义跨两次读取不会因此破坏；但残留的 7d 也可能吞掉下一帧的起始 7e。本轮“7d + 有效帧 A + 有效帧 B”例中，A 的起点被吞，直到 B 的未转义起点才恢复，不能承诺只损失当前一帧。

任何被识别为分隔符的未转义 7e 都优先于长度/body/CRC 当前状态，将长度、计数和临时 CRC 清零，重新读长度。若截断或错误长度还没有到 CRC，后来的未转义 7e 仍可直接放弃这段帧。若流持续缺少合适分隔符，恢复时间没有由本段解析器保证。

原指令：pass1/001d9e40.txt 001d9e68..001d9f20；001d9bc0.txt 001d9c38..001d9c40、001d9d18..001d9d38。

4. 长度边界：零长度不是成功空帧，超长不是直接丢弃

零长度：读完长度时直接把状态设为 body，并不立即去读 CRC。接下来的每个普通 token 都先 count++，再比较 count==declared_length。本轮有限的零长度输入中，线上两个 CRC 字节被当成 body；后续未转义 7e 才重新同步。这里没有把 64 位计数在极端长输入后的回绕推广为已穷尽结论。

超长：001d9d54..001d9d90 先取旧 count；仅旧 count < capacity 时才写 body[count]，但两条分支都会 count++。等 count==声明长度，照常进入 CRC。001d9cf0/001d9cf8 将配置 body 指针和完整 count 传给 CRC；001d9dd8 起按 count 次逐字节读取。

这意味着，声明大于 2048 且收到足够普通 body token 和两个 CRC token、期间未被未转义分隔符打断时，CRC 读取范围超出 2048 字节 body 子缓冲。以 2049 为例，第 2049 个 body token 不存储，CRC 却请求读 2049 字节。接收区从 owner+0x3170 开始，配置区末尾恰为 owner+0x3970；这之后仍可能是同一对象的其他字段。不能把“超子缓冲”偷换为“确定超出整个分配、确定可利用或确定崩溃”。

模型在这一点明确停止并标 native_outcome=not_modelled；不填造相邻 RAM、不强行宣称 CRC 必然失败。错误长度若先遇到未转义 7e，则不会沿此条件走到超范围 CRC；另有合成例说明这一差别。

5. 与上轮 USB 槽提前复用的关系

上轮 sensor-usb-packet-read 已证的是有前提的源 RAM 改写机会：旧发送未结束，提前复用槽，改写落在尚未复制到 PMA 的字节，且发生在对应复制之前。它不是一次现场坏包记录。本轮接上接收端后可以分为：

  A. body 某些字节变化而尾部仍为旧 CRC：本轮具体合成例被拒绝；后续未转义分隔符可恢复。没有对所有改写模式、长度或 16 位 CRC 碰撞作全局证明。
  B. 改写涉及长度或转义：可改变帧切分；下一帧起点可能被残留 escape 吞掉，也可能走到超配置 body 的 CRC 范围，不能归结为“最多丢当前帧”。
  C. 接收端获得另一份完整、自洽且 CRC 匹配的帧：LSP 层可接受。CRC 没有样本新鲜度、物理来源或主机 ACK 语义；还要看该帧的 opcode/payload 检查与更后的时间/序列逻辑。

这些是条件分析。未测到实机发生率、受影响通道数、睡眠分期影响或真实云端记录变化。
