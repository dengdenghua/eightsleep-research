传感异常组合 → 0x3c → Frank → 上传队列：有限链路结论
2026-11-08；离线合成模型。不执行固件、不访问设备/账号/网络，不生成畸形包，不研究共享日志格式缓冲/重入。

结论（置顶）

1. 时间对齐的核心风险被量化了：连续读失败期间，MCU 快照继续沿用旧 current，
   而 0x3c 包内没有新鲜度/CRC 成功标记；Frank 收到后仍按 header_tick + i*floor(1000/frequency)
   给每一行重建连续的新 tick。于是「旧值 + 新时间戳」一起进入上传链。
   14 个场景共 484 个旧值行/通道对，staleness 2..20 个软件 tick（名义毫秒，条件成立时）。
   数据清洗无法只靠包内时间戳或字段判断哪些是本次新转换。
2. 启停交错不解决旧值，反而制造整包旧值：stop 不清 current/队列，start 只清软件队列。
   「stop→start→连续 5 次 CRC 失败」场景里，恢复后的第一个包 5 行 40 个通道全是旧值，
   但仍被 mapper 推进 5 行、正常入队并发布。stop 前已齐备的一批，在 stop 之后仍被消费并发布。
3. 全器件重初始化也不清 current：reinit 只清器件对象（含 backup），并按原 active
   决定是否走 start 清队列。active=1 与 active=0 两条分支在本模型中都产出
   一个 40 通道旧值包；「清队列」不能清除旧值来源。
4. 「MCU 侧恢复」不等于「数据能上传」：队列预载 16 条时，恢复后生成的 4 个包全部被拒，
   published=0，队列里仍是最初 16 条外部条目。满拒新发生在 body 复制之前，不覆盖旧队首。
5. 发布失败只保留同一队首：失败后后续包排在后面，重连重试发布的是 SHA 未变的同一 body；
   logger 序号、发布次数与样本序号不是一回事。
6. frequency=0 是另一种「整包不进链」：Frank 把头字段写入协程局部对象并标记存在后提前退出，
   mapper_rows=0、不生成 body、不入队；这与队列满拒新是完全不同的阶段。

一、这次补上的缺口

既有两份工作各自完整但没有接通：
  - local-sensor-recovery-followup：MCU 故障/缓存/启停/重初始化状态链，30 个用例，
    产物停在 0x3c / 0x39 载荷；
  - integrated-capture-model：合成采样 → 规范 LSP → Frank CBOR → 发布队列，8 个场景，
    其中「保留旧值 / 丢批 / 队满 / 发布失败重试」是人为注入的条件。
本轮让 MCU 故障状态机驱动包序列，每行保留来源台账，再送进 Frank 载荷边界与发布队列。
两层之间新增的不是新固件证据，而是「故障事件 → 逐行来源 → 重建时间 → 是否入队/发布」的因果链。
逐条契约及其来源见 CONTRACTS.json，输入 SHA 见 SOURCE_MANIFEST.json。

三、对数据清洗与时间对齐的直接含义

  P0  旧值被赋予连续新 tick。crc_fail_10 场景中 80 个旧值通道对的
      staleness 从 2 递增到 20 tick；Frank 的 mapper 与 owner+0x3c80 计数
      按「解码行数」推进，不按「有效转换数」推进。因此仅凭 tick 连续性、
      包长或解析成功，无法识别这些行是重用的。
  P0  partial_ready 场景里同一行内 4 个通道新值、4 个通道旧值混合，
      包内同样没有逐通道新鲜度位。清洗规则若以整行为单位判定新鲜度会漏判。
  P1  启停交错会形成「整包旧值」：stop_start_stale_first_batch 的 pkt1
      header_tick=10010，5 行全旧，仍正常发布。stop 后的残批也照常发布
      （main 0x3c 只看队列数量，不看 active）。
  P1  失败/恢复/stop/start/reinit 交错场景出现两个旧值包（pkt1、pkt3 各 40 通道对），
      最大 staleness 16 tick；恢复事件之后并非立刻全为新值。
  P1  队列满时新数据整体进不了上传，旧条目占位。这与 NATS 接收层的 discard-old
      是不同阶段，不能合并成一个丢弃策略；也没有从模型推断实际丢包率。
  P2  frequency=0 时头字段已写入协程局部对象并标记存在，但本分支没有逐行 mapper
      输出。该结论限于所审 0x3c 分支，不排除其他协程/分支后续输出。

四、模型修正记录（可复现性）

首版按「通道 last-write 标签」判定新鲜度，把 CRC 失败后仍标着 new_conversion 的
沿用旧值误判为新值，导致所有故障场景旧值计数为 0，与既有代码结论矛盾。
已改为按「本次 callback 是否真的写入」判定：只有 source_tick == 本行 tick 才算
new_this_callback，其余分为 retained_current / backup_copy / initial_unset。
修正后 crc_fail_3=24、crc_fail_10=80，与「5 份记录可全部沿用 CRC 失败前 current」
一致。两次运行的差异是本轮实证过程的一部分，没有保留错误版本当结论。

五、边界与明确未做

  - 抽象 body 代替 30,128 B CBOR 编码；字节级 LSP/CRC/CBOR 贯通已由
    integrated-capture-model 的 8 场景完成，本轮不重复，也不声称新增字节证据。
  - 不含 core 队列消息、KV 状态协调、libnats ACK/MsgId、NATS raw_mem、
    uploader、TLS、云端接收与独立 PubAck 观测。
  - CRC/DRDY、stop/start/reinit、publish 返回码全部是显式输入，不是实机故障率、
    恢复成功率或时序记录；tick 是软件计数，不是墙钟测量。
  - 不研究共享日志格式缓冲/重入：该专项曾被自动安全检查中止并标记未验收，
    本轮没有重试、没有改写措辞、没有引用其草稿结论。
  - 实际部署版本、通道物理位置、真实采样率、同源输入/输出记录仍缺，
    生产生理算法与 Autopilot 不在本轮范围；USB 0x2B 生产者与旧波形 RAW writer 两个旧缺口保持原状。
