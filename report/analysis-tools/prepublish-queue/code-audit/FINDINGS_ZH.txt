Frank 发布前内存队列：代码审计
日期：2026-11-08

可以直接引用的结论

这份 MTK 固件中，原始数据进入 NATS 之前，还要经过 Frank 自己的内存发送队列。
已确认原始数据队列最多容纳 16 条待发送消息；它由 Stealth、Piezo 和若干健康状态消息共享。
这里的“16”不是采样点数、字节数，也不能直接换算成可缓存多少秒。
队列满时拒绝本次新消息；已审计的原始数据提交函数只记错误、释放本次临时数据并推进 logger 计数，未在该分支重试。
已经入队的消息则在 js_Publish 返回成功后出队；返回失败时保留队首、重建连接并等待约 1 秒后重新进入调度。
这与后续 NATS raw_mem 满时淘汰旧消息是两个不同阶段，不能混成一个丢弃策略。

这些是固件代码可证明的行为，不是这台实机发生过丢包的记录，也不能据此估算实际丢包率。
本次没有执行固件、连接设备、访问账号或网络，也没有恢复云端算法。

pass1/*.asm.txt 同时保存地址、原始指令字节和反汇编文本；*.refs.txt 保存函数引用。

导出覆盖指定队列函数、worker、构造函数及全局对象指针 0x005e3b98 的直接引用函数。
没有重跑完整程序分析，也没有扩大到 libnats 内部或全部异常清理/析构路径。

2. 四个队列和容量

W 是全局指针 DAT_005e3b98 指向的 worker 对象。以下偏移均以字节计。

用途                  W 内队列位置   环形 N 值  可同时等待的消息数
原始数据 JS 队列       +0x0c0         17         16
raw.log JS 队列        +0x200         1025       1024
raw.events.* JS 队列   +0x340         33         32
core 队列             +0x4c0         17         16

证据：pass1/0019a970.c:24-55；对应 asm:12-56 中可直接核对 0x11、0x401、0x21 和 0x11。
三个 JS 队列的指针表位于 W+0x480，轮转位置位于 W+0x498。
环形队列留一个空槽区分空/满，因此容量为 N-1，而不是 N。
JS 消息体另行按长度分配内存；0x498/0xe118/0x818 等是容器存储分配，不能当成消息体字节上限。
此容量只适用于本输入二进制，不能仅凭 Pod5/Pod6 名称推到其他固件版本。

3. 为什么确认是传感数据队列

pass1/001e9390.c:98-103 将 mask=1 映射为 raw.log，mask=0x10 映射为 raw.sens.piezo；
同文件:181-182 将 mask=0x04000000 映射为 raw.x.sens.stealth。
同文件:225-229 明确把 mask=1 送 W+0x200，其余 mask 送 W+0x0c0。
对应 asm:129-135、337-339 能直接看到 +0xc0 / +0x200 及对 001f49b0 的调用。
这已经把传感消息名称、raw 提交函数、入队函数和同一 worker 对象接在一起，不是仅凭函数名推测。

另有 pass1/00189000.c:61-72 的 raw.sens.health 使用 W+0x0c0，说明原始数据队列由多类消息共享。
pass1/002563b0.c:195、251-292 的 raw.events.* 使用 W+0x340。
pass1/0018b294.c:237、261-295 的 device.heartbeat.frank 使用 core 队列 W+0x4c0。
已确认至少一个 core 生产者为 heartbeat；本审计不声称它是 core 的唯一生产者。

4. 入队、满队列和内存归属

001f49b0 的参数 Q 为一个 JS 队列。布局：
Q+0x00=N；+0x08=存储；+0x40=写位置；+0x80=生产者缓存读位置；
+0xc0=读位置；+0x100=消费者缓存写位置。
下一写位置=当前写位置+1，达到 N 后回到 0。
若下一写位置等于缓存读位置，刷新实际读位置；仍相等就返回 0。
这个满队列判断位于 subject/body 的复制之前，不覆盖旧队首。

证据：pass1/001f49b0.c:18-27；asm:8-15、89-95。
asm 可见对实际读位置的 ldar 与成功提交写位置的 stlr；本报告不据此扩展证明任意多生产者并发安全。
成功时复制 subject，按消息体实际长度另分配空间并复制 body，最后提交新写位置，返回 1。
证据：同 C:28-107，asm:57。

raw 提交函数 001e9390 接到返回 0 后记录 Failed enqueue jsMsg，随后仍释放本次临时 body/subject、
推进 logger 计数并释放原编码缓冲，当前分支没有本地重试或回滚。
证据：pass1/001e9390.c:231-248。
这足以确认该提交调用在满时放弃本次消息；不能据此把这个 logger 计数直接等同于云端批次序号。
分配异常路径存在，未纳入本次行为模型；模型也不代表所有内存耗尽情形。

5. 发送顺序和失败后的行为

001afe00 首先检查运行标志 W+0x80，再尝试初始化/恢复连接。
连接初始化失败后，代码指定 1 秒 nanosleep，随后重新进入循环。
证据：pass1/001afe00.c:28-46、173-178；连接函数 pass1/001970e0.c。

每轮先处理 core。core 非空时，natsConnection_Publish 和 natsConnection_Flush 都返回 0，
才释放该条内容并推进读位置，之后直接回到循环顶部。
失败时保持该队首、清理连接状态、指定等待 1 秒再回到顶部。
证据：pass1/001afe00.c:48-104。
因此，若 core 持续非空，JS 队列可能持续得不到处理机会；这是条件性调度结果，不是实机负载结论。
这里的 core Flush 不等于原始波形获得云端确认。

core 为空后还要经过 KV 状态协调/待写状态处理，部分分支会回到顶部。
证据：同 C:106-172；辅助函数 0019feb0、001af7c0。
独立队列模型若未实现 KV，必须明确省略这一调度层，不能称完整 worker 仿真。

之后从 W+0x498 指定的起点最多扫描三个 JS 队列，选择首个非空队列的队首。
js_Publish 返回 0：释放该消息的 body 和 subject、读位置+1（到 N 回 0），
轮转起点设为“本次选中队列+1，模3”，清理返回的 PubAck 对象，再回到顶部。
非 0：不释放队首、不推进该队列读位置，也不改变轮转起点；清 KV/JS/连接状态，
指定等待 1 秒再回到顶部，由下一次循环重新连接并调度。
证据：同 C:179-248、261-266；subject 释放辅助函数 pass1/001998f0.c。

失败后仍然会重新扫描，而不是把 worker 永久锁在同一个 queue 指针上。
只有失败队列一直是每次扫描遇到的首个非空队列时，后面的 JS 队列才会持续被它挡住。
更靠前队列后来有消息、core 消息或 KV 工作都可能改变下一次处理对象。

“1 秒”是该分支配置的等待时间，不是失败重试的严格周期；连接调用、发布调用、调度和系统睡眠都会增加时间。
本次只用 publish_return_ok 表示 API 返回 0，不把它伪装为独立抓包观测到 ACK。
worker 调用 jsPubOptions_Init，未在该函数内看到逐条 MsgId 赋值，但尚未审计同包 libnats 的完整协议实现。
发布失败不证明远端一定没有接收。ACK 丢失后再次尝试、可能重复等，只能是明确标注的假设情景；
既不能宣称已经观察到重复，也不能宣称已经证明“只发送一次”。

6. 停止与进程生命周期：已证边界

运行标志为 0 时，001afe00 在循环顶部直接返回，没有队列遍历或排空操作。
正在进行的发布调用可能先完成，随后才到达下一次运行标志检查。
外层 00189bb0 在 worker 返回后清 KV/JS/connection；已审计函数内没有队列遍历、索引重置或逐条释放。
main 的可见关闭片段置 W+0x80=0 后 join 线程。
证据：pass1/001afe00.c:30-41；pass1/00189bb0.c:9-36；
pass1/00179600.c:676-680，asm:741-746（stlrb wzr,[W+0x80]）。

因此：停止 worker 不应在模型里直接等同“立即释放所有队列”或“自动排空”。
已审计代码是保留内存中尚未发出的条目；进程退出后这类内存条目不再存在。
外围全部析构/异常退出调用链未完成穷尽核对，故本报告不声称已经证明所有关机路径都无补偿落盘。
没有发现本队列路径内的落盘调用，不等于证明整个系统不存在其他备份机制。

7. 与既有分析的分层

原始数据编码完成 → 本次审计的 Frank 内存待发队列 → NATS 接收/raw_mem → 后续 uploader/云端。
本次“队列满拒新”发生在进入 NATS 之前。
旧 finishable-20261107/raw-upload/RAW_02_FINDINGS_ZH.txt 的 DiscardOld 是 NATS 接收层的淘汰策略。
旧 finishable-20261107/host-model/FINDINGS_ZH.txt 的 body_candidate 只到编码输出边界。
不能把三层合成一个容量、序号、重试或丢弃规则。

8. 下一步验收范围

现在可做：用已证容量、满拒新、发布失败保留、成功轮转、core 优先建立独立合成模型，
用固定输入复核每个分支；模型结果必须标“模拟”，不能写成设备采集结果。
接实机后：记录实际失败日志、提交频率、队列占用或可对应的消息序列，才有资格量化实际溢出和恢复耗时。
仍待核：外围析构/异常退出、同包 libnats ACK/去重语义，以及对应当前实机固件是否为同一字节版本。
生产睡眠分期、融合和云端策略的缺口未被本次队列分析解决。
